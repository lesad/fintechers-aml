# Decisions (ADRs)

> **Intended use:** an append-only log of architecture decisions. Add a new ADR whenever a non-obvious call is made. **Never edit an accepted ADR** — supersede it with a new one and annotate the old (`Superseded by ADR-NNNN`). Newest first. Keep entries short: the decision, its status, and _why_.

### ADR-0055 — Approving a rule version recalculates the alerts in the background, as an import's rule run does

**Accepted.** Once a version is approved (four eyes, ADR-0052) it is active, and `POST /api/rules/{id}/approve` starts recalculating the alerts with it before it answers: the import's rule run, on the import's single worker, so it waits for an import or recalculation already running. A new run with every active rule replaces the queue's alerts, and every decided case keeps its status, assignee and decision log (the import's carry-over); the cases still `NEW` from the previous run are recomputed, not deleted, and stay in that run as history. The job is recorded in `import_job` (migration 0029) with no file and `rule` naming the version, so the import history lists it. The UI says it started, follows the job and says how it ended, then reloads the queue. _Why:_ an approved rule should change the queue at once, not at the next import, and the import already knows how to rerun the rules without losing decisions. _Trade-off:_ a recalculation takes a full run (about 40 s on the July data); an import uploaded meanwhile waits behind it, and AI ratings of the recomputed `NEW` cases are not carried over.

### ADR-0054 — The rules tab becomes a Settings tab with sub-tabs, one path per section

**Accepted.** The header cog opens one tab, **Settings**, not a tab per configurable thing. Inside it an underline sub-tab bar switches between **Detection rules** (the rules page of ADR-0049) and **Triage scoring** (the triage config of ADR-0048). The section is part of the URL, not component state: `/settings/rules` and `/settings/triage`, so a reload, a shared link and Back all land on the section that was open. The tab strip still shows a single Settings tab; the tab remembers the section it last showed, so switching to a transaction tab and back returns to it rather than resetting to the rules. Both sections stay **mounted** while hidden, the same trick the tab strip uses, so a half-filled rule form survives a switch to the scoring and back. `/rules` is kept as a redirect to `/settings/rules` with the query string preserved, because the `?rule=<id>` deep link that the accepted rule suggestion links to (ADR-0040) is already in toasts and, potentially, in someone's history. The sub-tab bar is a reusable `components/SubTabs` (`role="tablist"`, arrow-key navigation), distinct from the top `Tabs` strip: a strip tab is a workspace the reviewer opens and closes, a sub-tab is a section of one. _Why:_ triage scoring is configuration like the rules are, and a second top-level tab for it would put two cogs in the strip and make "settings" mean two different tabs. _Trade-off:_ one more level of navigation, and the settings tab is now the only tab whose content depends on more than its id — `pathOf` needs the remembered section. Extends ADR-0039, ADR-0041 and ADR-0049; `/rules` as a page path is superseded by `/settings/rules`.

### ADR-0053 — Every proposed rule version says why it changes

**Accepted.** A rule version carries `changeReason` (migration 0027, `rule.change_reason`): what prompted the change and what it should achieve. Only a version that changes an earlier one needs it: `POST /api/rules` for an existing key and `PUT /api/rules/{id}` of a version above 1 answer 400 without one; a first version and the explanation preview do not. The rule form has a required "Why this change" field for those versions: a new version starts it empty, an edited draft keeps its own and can be saved for a new reason alone. The reason shows, beside "What it flags", on the screen of every version above 1 and in the regulator export; versions saved before this read "Not recorded". A draft saved from an AI rule suggestion takes the reviewer's false-positive reason that prompted it ("False positive on TX…: …"). _Why:_ a rule change is a monitoring decision the supervisor may ask to reconstruct, and the approver (ADR-0052) needs the author's reason to judge it. _Trade-off:_ the reason is free text the engine does not check beyond being non-blank.

### ADR-0052 — Four eyes on a rule version: the author picks an approver of the compliance officer's level or higher

**Accepted.** Refines ADR-0051. Sending a draft for approval names the approver (`POST /api/rules/{id}/submit` with `{"approverId": 3}`): a compliance officer or the compliance manager, never the version's author nor whoever sends it (`X-User-Id`); without one the engine picks the first compliance officer who is neither, and answers 400 when there is none. A compliance officer approves or rejects any pending version they did not write; the compliance manager only one sent to them; nobody decides their own (403). The rule screen shows the approver picker next to "Send for approval" with only the eligible people, and the Approve and Reject buttons only to whoever may decide. _Why:_ with one compliance officer seeded, a draft that officer wrote could never be approved; letting the author send it up to the compliance manager keeps four eyes without a second officer, and an analyst's draft still goes to the officer by default. _Trade-off:_ the compliance manager now decides a rule when one is sent to them, which ADR-0051 kept from them; triage configs still have no submit step, so their activation keeps ADR-0051's rule.

### ADR-0051 — Three roles as AMLR names them: analyst, compliance officer, compliance manager

**Accepted.** The two users become three roles (migration 0026): `ANALYST` (was `REVIEWER`, J. Novák), `COMPLIANCE_OFFICER` (was `MANAGER`, M. Svobodová) and `COMPLIANCE_MANAGER` (new, P. Dvořák, a board member). The analyst works the cases assigned to them, marks a case false positive or escalates it, and drafts rule versions and sends them for approval. The compliance officer decides escalated cases and reports any open case (false positive or report), is the contact person named in the FAÚ report, drafts rules, and approves or rejects rule versions and activates triage configs, but never a version they wrote: the engine answers 403 (`RuleService.approve`, `POST /api/triage/config/{version}/activate`), and the rule-score and factor patches, which activate at once, need the compliance officer in `X-User-Id`. The compliance manager sees every case (the queue is not scoped to an assignee) and decides nothing: no decision, no reassignment, no approval; they and the compliance officer open the FAÚ report, the analyst does not. Escalation and rule submission route to the first compliance officer. _Why:_ AMLR Art. 11 separates a management-body member who answers for AML compliance (compliance manager) from the person who runs it day to day and files reports with the FIU (compliance officer, Art. 69(6)); in practice the compliance officer owns monitoring and approves scenario and threshold changes, while the management body approves the policy and receives reports (EBA/GL/2022/05). Today's Czech names are the contact person (§22) and the board member responsible for AML (§22a). _Trade-off:_ with one compliance officer seeded, a version that officer writes waits for a second officer; the analyst's own drafts are the normal path. The checks still trust `X-User-Id`; there is no login. A triage patch is written and activated by the same officer, so four eyes there is still open.

### ADR-0050 — The FAÚ report is a printed draft built from code facts; the §20 hold is a recorded human input

**Accepted.** A reported case offers "FAÚ report (PDF)" in its Reported log entry: a printable suspicious transaction report (OPO) in Czech, laid out as FAÚ's OPO template (reporting entity; the client; the person acting for the client; executed or postponed; the transaction and its circumstances; further information; the person filing, with place, date and signature), built in the browser and printed with `window.print()`, like the rules export. It carries what §18 of Act 253/2008 asks for, and never names who detected or escalated the case (§18(3), INV-10): the decision log stays out, and the only person named is the manager who filed the report. The grounds are the hits whose rule window holds the reported transaction: the report reads each hit's rule version from `GET /api/rules`, anchors its variable windows on the hit's grain (a transaction id or a day) and keeps the hits that cover the transaction; a type C alert holds every C hit of the client, so the others go under further information. The evidence prints as Czech lines from the rule definition (aggregation, field, window, parameter unit), amounts in CZK; the client's transactions inside those windows and their counterparties are listed from `GET /api/transactions/{id}/history`. Identity data the dataset lacks (name, address, birth number or company id, identity document, nationality, payment purpose, representatives, counterparties' names) prints as a visibly marked gap, chosen by client type. The bank and the contact details are made up, like the app's users. No model output goes into the report (ADR-0032); the triage reasons stay out as internal scoring. The Report form asks whether the client's order is postponed under §20 (no default) and asks for the reason in Czech; `case_event.postponed` stores the answer with the decision (migration 0025). _Why:_ FAÚ takes an OPO on its form by data box or through MoneyWeb, in Czech; we cannot file, so the report is a draft for the contact person that shows what the case already proves and what is still missing. _Trade-off:_ the window table lists every client transaction inside the rule's windows, not only those a variable's filter counted, because the filters are rule expressions the frontend does not evaluate.

### ADR-0049 — A backtest replays the rules twice in a rolled-back transaction and keeps its result in its own tables; rules and backtests are tabs

**Accepted.** `POST /api/rules/{id}/backtest?from&to` replays a period with a draft: the production rule run (`RunService.run`, with triage and routing) runs once with the active rules and once with the draft in place of the active version of its key and scope (or added, for a new key), inside one transaction that is always rolled back, so no production run, alert or case is left. The two runs are compared per transaction, counting a case as flagged when its most severe disposition is not `AUTO_CLOSE`: `NEW`, `DROPPED`, `RAISED`, `LOWERED` or `UNCHANGED`, with a note when the draft's rule no longer fires. The replay runs in the background on one worker thread: `POST` checks the draft and the period, deletes every stored backtest (only the latest one is kept, whatever draft it was for), records the new one as `RUNNING` and answers 202 at once; the result lands as `DONE`, or `FAILED` with the reason, and a backtest deleted while it runs drops its result. A backtest still running when the engine stops is marked failed at the next start. The UI polls `GET …/backtest` every 2 s and shows a spinner in the tab until then, so a reload of the tab comes back to the waiting screen or the result. The result is stored apart from production, in `backtest` (the summary and its status) and `backtest_row` (migration `0024`); `GET …/backtest` reads the summary and `GET …/backtest/rows?view=all|changed|new|dropped&page&size` pages and filters the rows on the engine, since a month can affect tens of thousands of transactions. A backtest goes with its draft: deleting the draft cascades, and a trigger on `rule` deletes it once the version leaves `draft` and `pending` (approved, active, retired); while pending, the approving manager can still see it. `DELETE /api/rules/{id}` deletes a draft. In the UI the rules page is a tab (`/rules`, opened by the header cog) and a draft's backtest opens its own tab (`/backtests/:draftId`), after the updated Claude Design; a draft gets Delete and Backtest (a period within the data, July 2026). _Why:_ reusing the production run is the only way the backtest sees exactly what production would, a rolled-back transaction gives that without a separate code path, and storing the comparison apart keeps backtest data out of the case tables. _Trade-off:_ two full runs: about 35 s for a week of July, a minute or more for the month; one backtest at a time, so a second one waits for the first (whose result is then dropped); progress is only running or not. Extends ADR-0041.

_Amended: the rows no longer carry a note (migration 0028); the change label says it._

_Amended: both runs cover all the data, as a production run does, and the rows are every transaction of the chosen period, unchanged ones included. A transaction takes the highest rating of the open alerts it belongs to: the transaction a hit was about, the anchor, every transaction of the client's day for a day hit, and the transaction the alert points at. A backtest takes as long as two full runs, about 100 s._

_Amended: a changed row says why: `byRule` when the rule itself is about the transaction (as the draft or as the version it replaces), `byTriage` when it is not, or when its alert also holds other transactions whose hits weigh in that alert's triage; both may hold (migration 0028)._

### ADR-0048 — Triage config is versioned data in the database, normalized into columns and child tables

**Accepted.** The triage config leaves the classpath (`engine/src/main/resources/triage/triage-config-v1.json` is deleted, with `TriageConfig.load()` and `TriageConfig.parse()`) for eight insert-only tables, migration `0023`. `triage_config` is one row per version with the flat policy scalars as real columns — `unknown_rule_score`, `per_extra_rule`, `extra_rule_max` and the eight factor weights (`factor_pep`, `factor_high_risk_country`, `factor_static_cap`, `factor_unbaselined_client`, `factor_tenure_under_90_days`, `factor_tenure_under_365_days`, `factor_per_extra_alert_type`, `factor_extra_alert_type_max`) — plus `status`, `author`, `approver` and timestamps. Everything list- or map-shaped is a child table keyed on `config_id`: `triage_rule` (`base_score`, `auto_closeable`, `implies_pep` per rule key), `triage_risk_point`, `triage_channel_point`, `triage_amount_band`, `triage_intensity_band`, `triage_band`, `triage_required_field`, `triage_floor`. `TriageConfig` loses `baseScores`, `autoCloseWhitelist` and `pepImpliedByRules` and gains `ruleTriage: Map<String, RuleTriage>`; `Triage.decide` is unchanged beyond four lookups against it, so the six steps, the reason codes, the clamp and the input hash all stand. `configVersion` is not stored: the repository builds it as `triage-v<version>`, so the seeded version 1 reads `triage-v1` and the `alert_triage` rows already written need no backfill. `ruleNames` and `alertTypeNames` still come from the `rule` and `alert_type` tables and stay presentation only. _Why the config left the jar:_ rules are added at runtime through `/api/rules` (ADR-0027, ADR-0035), but their scores were compiled into a file shipped with the jar, so every new rule silently fell to `unknownRuleScore` 70 plus the `UNKNOWN_RULE` floor and only a rebuild could fix it. Tuning the policy a regulator asks about should not be a deploy.

**Columns and child tables, not one `jsonb` payload.** The first cut of this migration stored the rule-agnostic policy as a single `payload` document. It is rows now, for four reasons. _The UI that comes next edits one field._ Changing one band's `max_score` or one rule's base score should send that field; against a document the client has to read the whole config, splice, and send it all back — and two reviewers doing that concurrently silently clobber each other, last write wins, with no column-level evidence of what was lost. _Ordering is now explicit._ Amount bands, intensity bands, score bands, required fields and floors each carry a `position` column, the pattern `rule_variable` already uses; it preserves the **authored** order, which is exactly what the old JSON array order meant. Reading children back `order by config_id, position` is what guarantees no behaviour moves — including the order of `FLOOR_` and `DATA_MISSING` reason lines. _Invariants become SQL._ Score ranges (0–100), non-negative amounts and caps, the five dispositions, the four required-field names, the four floor conditions, and `(condition = 'ALERT_TYPE') = (alert_type is not null)` — the SQL twin of `TriageConfig`'s existing `init require` — are `check` constraints. The Kotlin `init` block stays the single validation gate for anything constructed in the JVM; the constraints catch what reaches the database by any other route. _Diffing two versions is a join_, not two documents parsed in the application. _What it costs:_ eight tables where there was one column, a `load` that issues one query per child table and assembles the object, and insert code that writes eight tables instead of one — noticeably more mapping code than `jsonb`, paid once, against an edit path used continuously. `highRiskCountries` deliberately gets no table: it is not policy stored here, `TriageService` overlays it from `reference_list` at decision time, and the repository returns an empty set, exactly as the old payload's empty array did.

**A separate table, not columns on `rule`.** `triage_rule` does not extend the `rule` table. Detection and triage policy are two decisions with two owners and two review paths: what a rule *detects* is the engine's (condition, variables, parameters, checks), what a hit is *worth* is the second layer's, and the same rule's score can change without the rule changing. The `rule` table also belongs to the engine's immutable-version contract (ADR-0035) — a re-score would force a new rule version, and with it a new `rule_id` on every hit. _Trade-off:_ reading a rule's score is a join, and the two version counters move independently.

**Keyed by `config_id`, not by rule key.** Every child row hangs off the config *version* that owns it, exactly as migration `0012-params-on-query.sql` moved `rule_param` off `rule_key` onto `rule_id`. The lesson is the same: a child keyed by a text key belongs to every version of that key at once, so there is no way to change one version's value without rewriting history, and a reader has to re-derive which parent it meant. Keyed by the parent row's id, a config version is a closed, self-describing set of scores, bands and floors. There is deliberately **no foreign key** from `triage_rule.rule_key` to `rule`: `rule` has no primary key on `key` alone (it is keyed per version and scope), and a retired config version has to stay readable after its rule key is gone from the live set — a past decision must still be explicable. Coverage is reported instead of enforced: `GET /api/triage/coverage` names live rules with no score and scores no live rule uses. Child rows are never deleted, so no cascade is declared.

**Insert-only, like `rule` — and a patch is still a new version.** Versions are never edited and never deleted; a change is a new row with its own `status` (`draft`/`approved`/`active`/`retired`), `author`, `approver` and timestamps, and code assigns the version number (`max + 1`) — the caller never supplies one. A partial unique index enforces one `active` row. Only a status transition ever issues an `UPDATE`. The approval step itself is another work stream's; this implements `draft → active` and mirrors the columns. Normalizing does **not** make the config mutable: the one-field endpoints — `PATCH /api/triage/config/rules/{ruleKey}` and `PATCH /api/triage/config/factors` — derive the next version from the active one with `TriageConfigRepository.copyAsDraft`, apply the single change, and activate it, in one transaction. The copy happens in SQL (`insert into <child> (config_id, …) select <newId>, … where config_id = ?`) — no document is read into the JVM and rewritten — which is what makes a one-field edit cheap while history stays whole. The result is loaded back so `TriageConfig`'s `init` runs over it: a patch that would produce an invalid config rolls the transaction back and the previously active version is still active. Whole-document `POST /config` remains the way to edit the collections (bands, floors, amount and intensity bands, required fields); there are no per-element endpoints yet. A new version affects the **next** run only: nothing re-triages, and `alert_triage` keeps the `config_version` each decision was taken under. _Why:_ the point of versioning the config (ADR-0033) was that a decision taken months ago stays explicable under the policy that produced it — editing a row in place, or retroactively rescoring, destroys exactly that. _Trade-off:_ fixing a wrong score does not repair the alerts already scored with it; someone has to re-run triage deliberately, and a one-field patch still burns a version number, so the version log grows faster than "a release of the policy" would suggest. Supersedes the "base score per rule key, tuning in `resources/triage/triage-config-v1.json`" part of ADR-0033; the rest of ADR-0033 — the pure function, the six steps, the floors, the input hash — stands.

### ADR-0047 — The AI Rating's number check accepts an input number rounded to a whole number

**Accepted.** Refines ADR-0046 and, for the AI Rating only, ADR-0037's exact number check. A number the model writes without decimals counts as known when some number in the input rounds (half up) to it: `1,032,539` for `1032539.3`, `39,919` for `39918.96`. A number with decimals must still match exactly, and a number no input value rounds to is still a warning. The rule suggestion and the rule explanation keep the exact check. _Why:_ the model drops haléře from amounts the input holds despite the prompt, and each such rounding showed as an unverified number next to the real hallucinations, so the marks stopped meaning anything. _Trade-off:_ a whole number the model made up passes when it happens to equal a rounded input value.

### ADR-0046 — A number the input does not hold is a warning on the AI Rating, not a rejection

**Accepted.** Refines ADR-0043 and ADR-0034's number check for the AI Rating. The claim walker still refuses a claim without refs or with a ref outside the alert's activity. A number in model text that the input does not hold no longer refuses the result: it stays `ready`, and `body.warnings` lists `{at, message}` per field (`summary[0]`, `openPoints[1].normal`). The card shows that text with a dotted underline and the reason as a tooltip. Numbers stated in the system prompt itself (e.g. "within 24 hours") count as known. The summary may have up to six items; the prompt still asks for one to three. The rule suggestion keeps rejecting unknown numbers (ADR-0036). _Why:_ six of seven rejections this morning were a fifth summary sentence, the prompt's own "24", or an amount the model converted correctly from stale evidence; each one left the reviewer with no report at all. _Trade-off:_ a wrong number can now reach the reviewer, marked as unverified rather than hidden.

### ADR-0045 — The AI Rating shows the newest stored result; the summary kind is retired

**Accepted.** Refines ADR-0043. `GET /api/alerts/{id}/assessment` and the queue's `aiRating` read the newest stored result of the alert, whatever prompt made it; the prompt hash stays on the row as a record but no longer filters. A new result is generated only when none exists or when the reviewer clicks "Regenerate" on the card. The open points go from one to three to zero to three: none when the facts settle it. The summary stays a list of one to three claims, so the claim walker still checks refs per sentence, and the card shows it as one paragraph with the refs after it. The `summary` kind (`prompts/alert-summary.md`, `SummaryService`, `GET`/`POST /api/alerts/{id}/summary`) is retired; its stored rows and migration 0020's check constraint stay. The rule suggestion reads the latest ready AI Rating instead (ref `assessment`: rating, verdict, summary, open questions), and its prompt says the reviewer's reason wins over it. _Why:_ a prompt edit made every stored rating read as not run, so the queue and the cards emptied and every open of a detail paid for a new Bedrock call; nothing generated summaries any more, so the suggestion always got null. _Trade-off:_ a card can show a rating from an older prompt until someone regenerates it; `promptHash` on the envelope says which prompt it was.
### ADR-0044 — A rule version is approved by a manager before it runs

**Accepted.** Anyone creates and edits a draft rule version. Anyone can send a draft for approval (`POST /api/rules/{id}/submit`). It then becomes `pending`, is assigned to the first manager (`min(id)` with role `MANAGER`, the same as escalated cases), and can no longer be edited. Only a manager, named by `X-User-Id`, can act on a pending version. `approve` makes it `active` at once, retires the key's previous active version in the same transaction, and records `approver` and `approved_at`. `reject` returns it to `draft` with no assignee, so anyone can edit it and send it again. Anyone else gets 403, and a version in the wrong status gets 400. Migration 0022 adds `pending` and `rule.assignee_id`. A manager may approve a rule they wrote. The `approved` status stays unused, because approval is activation (GLOSSARY "approval"). _Why:_ rule changes alter what gets flagged, so a named second person must sign them off, and the demo has a single manager. _Trade-off:_ there is no four-eyes check, so a manager can approve their own draft. There is no choice of approver and no reason on a rejection. Approval does not re-run the rules; the next run picks up the new active version.

_Partly superseded by ADR-0051: the compliance officer approves, never a version they wrote._

### ADR-0043 — The AI Rating is one model output per alert; a refused reply is a result, not an error

**Accepted.** Refines ADR-0034. One call per alert returns the AI Rating: a rating (`high`, `medium` or `low`), a verdict from a fixed list of ten, a summary of one to three sentences and one to three open points, each with the question, what points to suspicion, the normal explanation, what would settle it and whom to ask. The call goes through `ai/AiGenerator` and returns the `AiResult {alertId, kind, status, body, error, modelId, promptHash, inputHash, createdAt}` envelope that the summary uses too. The claim walker checks every claim `{text, refs}` (refs present and in the alert's activity, numbers present in the input) and the free text of the open points (numbers only); enums and list sizes are checked again in code. The facts the model reads beyond the rule hits come from `AlertFacts`, computed in code: the client against its Q2 baseline, the counterparties, the money flow and the client's other alerts. Ratios arrive as text, so the model quotes them and never works them out, and the facts' refs join the refs a claim may cite. The prompt gets one focus paragraph per triage disposition. `GET` returns only a result written with the prompt of the alert's current disposition (the prompt hash), so a changed prompt reads as not run. The rating is High, Medium or Low advice shown next to the rule rating. Triage, priority and queue order never read it. This supersedes ADR-0032's "AI only writes summaries and rule proposals" for display only; triage, priority and routing still take no model input. `POST` returns 200 with `status: "rejected"` and the check's message when the reply fails the checks, and `status: "failed"` when Bedrock or the AWS SDK fails; both are stored and `GET` returns them. `GET` returns 404 until the kind ran once. Every result is stored in `ai_result` (migration 0020, which takes over and drops `alert_summary`). The transaction detail shows one AI Rating card per alert, the triage alert first, each generated from `/assessment` when the detail opens. The rule-suggestion endpoint keeps its 502 (ADR-0036) for now and can move to the envelope later. _Why:_ one run gives the reviewer the model's read and its open questions together, the reviewer wanted a rating at a glance, and a regulator wants a written, traceable rationale; a stored rejection also shows what the model wrote wrong instead of a bare 502. _Trade-off:_ a client can no longer tell a refused reply from a good one by HTTP status; it must read `status`. A rating from a model can read as authority, so the UI keeps it beside the rule rating and no code path acts on it.

_Refined by ADR-0045 (`GET` and the queue no longer filter by prompt hash; zero to three open points; the summary kind is retired)._

### ADR-0042 — Cases are assigned by code, and their decisions live in an engine log

**Accepted.** Every alert carries an `assignee_id`, and a case (a transaction in a run) has a decision log, table `case_event` (migration `0019`): when, who (`actor_id`, null for the engine), what (`ASSIGNED`, `REASSIGNED` or the status a decision set), the reason, and who works the case afterwards. Routing is code, run right after triage (`TriageRepository.route`): a case triage escalated goes to the manager and any other case to the reviewer, with the engine's own log entry; a case already assigned is left alone. `PUT /api/transactions/{id}/status` now needs a `reason`, logs the decision, and escalating hands the case to the manager in the same statement. `PUT /api/transactions/{id}/assignee` (`{"userId": …}`) lets anyone hand an open case to another user, which is logged as `REASSIGNED`; a closed case (false positive or reported) answers 409, and the UI shows no "Change" on it. `GET /api/transactions/{id}` returns `assignee` and `log` (newest first). `GET /api/transactions?assignee=<id>` keeps only that user's cases and scopes `countsByRating` to them; the review queue sends the signed-in user, so everyone sees just their own cases, in every status. This replaces the per-role status scope of the queue (reviewer: new and false positive; manager: escalated and reported, by `X-User-Id`), because a case reassigned outside its role's statuses would vanish from its new assignee's queue; the status filter matches the case status, as that change made it. _Why:_ with two users, who works a case follows from the triage verdict and the escalate button; assignment and the reason have to survive a reload and be auditable, which the browser-only decisions could not do. _Trade-off:_ the role is still found by role name (`min(id)` of `MANAGER` / `REVIEWER`), which holds only while each role has one user; the browser keeps its in-session decisions as an overlay on the queue rows and counts until the queue reloads.

### ADR-0041 — The active transaction tab is in the URL

**Accepted.** `/transactions/:id` is the overview with that transaction's tab active. Opening a transaction (a queue row, a history row, the header jump) or clicking a tab adds a history entry, so Back returns to the list or the previous tab and Forward comes back; closing the active tab replaces the entry with the tab that takes over, and a Ctrl/⌘ click opens a tab in the background without touching the URL. A reload or a shared link opens the transaction. The list of open tabs stays in memory: Back to a tab that was closed opens it again. `useTabs` (core) takes the active tab and a `go` callback rather than holding it, so it stays router-free; `src/app/use-app-routes.ts` wires it to the URL. Leaving `/rules` with the cog returns to the overview path it was opened from. _Why:_ reviewers expect the browser's Back to leave a detail for the list. Supersedes the "tabs are not in the URL" part of ADR-0039.

_Extended by ADR-0049: the rules and backtests are tabs with their own paths too._

### ADR-0040 — Rule suggestions: drafted from the reviewer's reason, checked, never saved

**Accepted.** Applies ADR-0032 and ADR-0034 to rule changes, on the versioned parameters of ADR-0035 with their units (ADR-0036) and amounts in CZK (ADR-0037). `POST /api/alerts/{id}/suggestion` takes the reviewer's false-positive reason and returns a `kind`: `rule_version` (a new version of a rule that hit, with its condition, variables and parameter values) or `none` (no change fits). A threshold change is a `rule_version` too. The model may only touch the client and company layers; the reason is a required citation, so an explanation that does not cite it is rejected. The same reply carries `ruleExplanation`, the new rule in plain English, held to the checks of a stored rule explanation (starts with "Flags", at most 500 characters, only known numbers), so the reviewer reads the change without a second model call. Its input is what the review already has: the reviewer's reason, the alert's hits, its triage, its stored AI summary, the rules that hit and every rule version that is not retired, drafts included; nothing else is mined for it. It answers `none` when the reason is a one-off or names no pattern, or when an existing rule or draft already makes the change. The model names the rule key, layer, condition, variables and the parameters it changes or adds. Code fills the rest. A client-layer change of a company or segment rule gets its own key, `<key>-<client id>`, which replaces the rule for that client, because a key keeps its layer, scope and `replacesKey` across versions. Code also sets the version (the key's latest plus one), the full parameter map (the base rule's values and units plus the proposed values; a new parameter names its unit) and `retires` (the active version of the same key). The checks compile the condition, build its SQL for the alert's client and simulate rule resolution with the change applied, so a suggestion that would not reach the client, or would drop clients the retired version covered, is rejected. A text comparison the model adds (`tx.type != "..."`) must use a value the field takes in the data; code lists those values for the enum-like fields and gives them to the model. A failed check or a Bedrock error returns 502. Nothing is persisted: `rule` has the shape of the `/api/rules` POST body without `author`, so accepting a suggestion can save it as a draft. `tx.month` and `day.month` join the rule vocabulary, so a seasonal reason ("this client sends rent every July") can be written as a condition. _Why:_ ADR-0032 and ADR-0034 allow suggestions, but only as checked proposals; code owns everything the model could get wrong in a way that changes behaviour. Code then reruns the drafted rule over the alert's run and compares its hits with those of the rule it replaces: it counts the hits it stops and adds and the alerts it closes (an alert closes only when all its hits stop), split by triage disposition, for the client and, for a company change, for every client. Code turns a valid draft into `none` with a `declined` reason when it would not stop this alert, would close an alert triage rated high or escalated, would raise new hits, or would stop fewer than `suggestion.min-hits` (default 2) hits, this alert's included: alerts of a per-client type hold all of the client's hits, so counting other alerts only would rule out every client change. _Trade-off:_ triage stands in for past false-positive decisions, which only the browser holds; the measure covers one run, so a monthly pattern shows a single hit and is declined as low impact.

### ADR-0038 — Parameter units are amount, percent and multiple

**Accepted.** The `count` unit is gone (migration `0016`); a parameter is an `amount` (CZK), a `percent` or a `multiple` of a client figure. _Why:_ no rule used `count`, and an option nobody picks only invites the wrong pick: a factor saved as `count` would read as "5 payers" instead of "5 times". A future rule that needs a plain number of things brings the unit back with its first use. Supersedes the `count` unit of ADR-0036.

### ADR-0037 — Money is CZK as a double, end to end; haléře are gone

**Accepted.** Every amount in the system is CZK as a floating-point number, the unit and shape the source CSV already delivers: `transaction.amount`, `client.expected_monthly_volume`, `client.q2_volume`, `client.q2_max_tx` and `rule_param.value` are `double precision` (migration `0015`), the importer stops multiplying by 100, the CEL vocabulary types amounts and parameters as `double`, triage carries `Double` and the API hands the browser plain CZK (`amount`, `expectedMonthly`, `q2Volume`, `q2MaxTx`) with no conversion left in the UI. Thresholds keep their value in the new unit: `pep_min` is 100 000, `country_min` 10 000, `min_inflow` 100 000, and the triage amount bands are 1 000 000 / 250 000 / 50 000 CZK, so no alert changes its outcome. _Why:_ one unit from the CSV to the screen. The haléře integer existed to keep arithmetic exact, but it was converted back for every reader — the UI, the rule form, both prompts, the summary number check — and each conversion was a place to be wrong; the thresholds the business states are CZK too.

**What this costs, and what guards it.** IEEE doubles are not exact in decimal, so sums over many transactions can differ in the last heller. The guards: the importer rounds to the heller at the boundary (`toCzk`, `Parsing.czk`), every amount that leaves the engine as text goes through one rendering (`plain`/`plainDecimal` — no exponent, no trailing `.0`, so `25.0` and `25` are the same string), and evidence is written as a plain decimal rather than Jackson's `1.1E7`. `CanonicalJson` no longer rejects floats; it renders them through `plain` and rejects NaN and the infinities instead, so the triage input hash stays stable and reproducible. CEL has no mixed int/double arithmetic, so a condition that multiplies an amount uses a double literal (`day_volume * 100.0`) and converts a count (`double(client.q2_days)`); the seeded conditions were rewritten in the same migration. Supersedes the money representation in ADR-0033, the haléře reading of ADR-0036's `amount` unit, and the `bigint` haléře in `docs/engine/rules-engine-design.md`. The unit column itself stands: `amount` now means CZK, and `percent`, `multiple` and `count` are unchanged. _Trade-off:_ an exact decimal (`numeric`/`BigDecimal`) would keep the arithmetic exact, but CEL knows only `int` and `double`, so a rule would convert anyway — the exactness would stop at the rule engine's door.

### ADR-0036 — A rule parameter stores its unit

**Accepted.** Each `rule_param` row carries a `unit`: `amount` (haléře), `percent`, `multiple` or `count`, required on save and fixed with the version (ADR-0035). The API sends a parameter as `{value, unit}`; the rule explanation prompt states the unit on each parameter line, and the alert summary input gets a `units` map next to the evidence. _Why:_ every reader of a threshold, both models and the frontend, guessed the unit from the name or the size of the number (the rules page read values from 100,000 up as haléře), and a percentage read as haléře turns "80 %" into "0.80 CZK". _(The `amount` unit is CZK since ADR-0037; `count` is gone since ADR-0038.)_ Code knows the unit so no model or screen has to infer it.

### ADR-0035 — Parameter values belong to the immutable rule version

**Accepted.** A rule version fixes its condition, variables and parameter values together: `rule_param` is keyed by `rule_id`, and changing a threshold means saving a new version. A segment or client that needs a different threshold gets its own rule version at that layer that replaces the company rule (`replaces_key`), the way suppression already works; per-parameter overrides are gone. A run fails, naming the client and the rules, when two rules at the same layer replace the same key for one client. _Why:_ a stored explanation, a hit's evidence or an audit entry must describe exactly what ran, and a rule whose thresholds could change under it cannot promise that. Supersedes the parameter-override half of ADR-0027 and the parameter layering in `docs/engine/rules-engine-design.md`.

### ADR-0034 — A model may judge, summarise and suggest; it never counts, computes or decides

**Accepted.** Refines ADR-0032. Every model call in the engine (Bedrock today) is limited to three jobs: a typed judgement code asked for, a summary of facts code collected, and a suggestion a person or the engine's checks accept or reject. It never counts, does arithmetic (sums, ratios, percentages, min and max) or decides an outcome (detection, triage, disposition, filing). Code prepares every number the model may quote: counts, ranges and converted amounts arrive in its input. The prompt says so, and code enforces it on the output: refs must exist in the input and numbers must appear in it. _Why:_ the alert summary showed the failure. Given 54 raw hits, Sonnet reported per-rule counts of 15 and 26 where the data held 18 and 23, in fluent text an analyst would trust. A prompt rule alone did not stop it; giving the model the counts did. _Trade-off:_ the code-side number check matches values, not meaning, so a wrong number that equals another input value passes. Precomputing in code is the real guard.

### ADR-0033 — Triage is a deterministic pure function over an alert; config is versioned data

**Accepted.** Implements ADR-0032's "triage is code" for the engine. Every alert gets a disposition — `AUTO_CLOSE`, `REVIEW_LOW`, `REVIEW_MEDIUM`, `REVIEW_HIGH`, `ESCALATE` — from `Triage.decide(input, config)` in `engine/.../triage/`, a pure function with no clock, no connection, no model and no randomness. Six steps in a fixed order: base score per rule key, risk factors, score-to-band, the auto-close gate, the missing-data floor, then the hard floors. A floor is applied with `maxOf` over the enum ordinal, so it can only ever make an outcome stricter. Everything time-shaped arrives on the input (`asOf` is the run period's end, never `now()`); money stays `Long` haléře and `CanonicalJson` throws if a float reaches the input hash. _(Money representation superseded by ADR-0036: amounts are CZK doubles and `CanonicalJson` renders them through one plain decimal form.)_

**One scale, not two.** ADR-0032 describes triage as `FP`/`REVIEW` plus a separate priority scorecard; this collapses both into a single ordered disposition with the score attached. `AUTO_CLOSE` is the old `FP`, and the three `REVIEW_*` levels carry what the scorecard's bands carried. _Why the change:_ two numbers that can disagree (a `FP` with a high priority) need a tie-break rule nobody had written, and the floors — the part a regulator actually asks about — only make sense against one ordered scale. The scorecard's factor vocabulary (rating, PEP, country, amount, tenure, channel, multiple flags) is kept as the risk factors.

_(The config's home is superseded by ADR-0048: the policy is the insert-only `triage_config` table and its seven child tables — `triage_rule` among them — editable through `/api/triage`; the classpath file is deleted. Versioning, validation and the stored `config_version` are unchanged.)_ Tuning lives in `resources/triage/triage-config-v1.json` under a `configVersion`, validated on load. Changing a number means a new file and a new version, so decisions already taken stay explicable under the config that produced them. Each decision stores its reasons, `config_version` and a SHA-256 `input_hash` over a canonical serialisation, in `alert_triage` — a separate table, so a run can be re-triaged (`bootRun --args=triage`) without touching detection output.

**Only what the data supports.** A factor ships only if this dataset can support an interpretation of it; one that cannot is not carried as a disabled knob, it is not written. Two were cut on that rule: the amount as a ratio of the client's declared monthly volume (the generator draws `amount = exp_vol/exp_cnt × exp(N(0,1))`, so the ratio is substantially a proxy for declared transaction count — r = −0.563, R² = 0.317 against `expected_count`) and points per legal type (no weight derivable, and type moves behaviour only through declared size, which the amount factor already counts). The sanctions floor went the same way: there is no sanctions list in the data, and a floor that can never fire is not a control.

_Why:_ an AML disposition has to be defensible to a regulator line by line, which rules out a model and rules out hidden state; the hash plus the config version make any past decision reproducible. _Trade-off:_ the weights are a judgement call, not a fit — the data carries no labels — so they are data rather than code, and expected to be re-tuned. Supersedes the paper scorecard in `docs/rules/priority.md`.

### ADR-0032 — Triage is code; AI only writes summaries and rule proposals; `docs/rules/` follows the engine

### ADR-0019 — Lint policy: `type` over `interface`, PascalCase component files, and the test-relaxation block covers every test suffix

**Accepted.** Three `.oxlintrc.json` changes, ported from a downstream fork that had hit each of them.

**`typescript/consistent-type-definitions: ["error", "type"]`.** One way to declare an object shape, so an agent never has to pick. Exactly one exemption — `global.ts`, because module augmentation (`declare module "next-intl" { interface AppConfig … }`) cannot use a `type` alias — plus `src/components/ui/**` (shadcn output, below). `src/core/test/ids/tree.ts`'s `TestIdNode` was the only production `interface`; converting it **widened** one cast rather than removing it (`Object.entries` on a `type` widens the value to the union of the declared members, which doesn't overlap `TestIdNode`, so the assertion must route via `unknown`) — the trade accepted for the single-form rule.

**PascalCase component filenames** — `unicorn/filename-case: pascalCase`, scoped to `.tsx` files under `src/components/`. Component files are named for the component they export. The shadcn `ui/` folder is exempt: it generates kebab-case and `pnpm dlx shadcn add` must stay a no-edit operation; the same block also exempts `consistent-type-definitions`, `jsx-a11y/label-has-associated-control` and `react/no-array-index-key`, all shadcn-upstream conventions. That block must stay **last** in `overrides` — oxlint applies overrides in order and the later match wins per rule, so an exemption placed before the rule that grants it is silently dead. Everything under `src/features/` keeps kebab-case: the rule is scoped to the reusable layer, where one file = one exported component actually holds.

**The relaxation block now lists `*.spec` and `*.e2e`, not just `*.test`.** It had covered `*.test`/`*.stories`/`tests/**`/`src/core/test/**`, so this repo's own integration specs and Playwright tests were held to production rules — an oversight, not a policy. `no-await-in-loop` is off there too: sequential awaits are the normal shape of a spec.

_Why:_ each was a real papercut downstream, and lint config is exactly the kind of thing a template should get right once. _Trade-off:_ the `unknown`-routed cast in `tree.ts`, and a per-zone override ordering constraint that is invisible in the file itself (hence the comment on the last block — oxlint parses JSONC, so `//` comments are legal there).

_Superseded in part by ADR-0028: shadcn/ui and its `src/components/ui/**` exemptions are removed._

### ADR-0018 — Track Next 16's stable conventions: `proxy.ts`, top-level `typedRoutes`, no `globalNotFound` flag

**Accepted.** Three corrections where `next.config.ts`/`src/` had drifted behind what Next 16.2.4 actually does.

**`src/middleware.ts` → `src/proxy.ts`** (default export renamed `middleware` → `proxy`, `src/middleware.test.ts` → `src/proxy.test.ts`). Next 16 renamed the file convention; the old name still works but emits a build-time deprecation (`warnOnce`, with a `@next/codemod middleware-to-proxy`), and `next build`'s output already labels the entry `ƒ Proxy (Middleware)`. The one constraint that mattered: **the `proxy` runtime is always `nodejs` and cannot be configured** — no problem here, since both things the file does (next-intl's middleware and the Supabase `updateSession` refresh) run on node. An app that needs the `edge` runtime must stay on `middleware.ts`. `@/supabase/middleware` keeps its name — it's our own helper, not the Next convention.

**`typedRoutes` moved out of `experimental`** — stable in Next 16.

**`experimental.globalNotFound` dropped.** The flag was a **no-op** on 16.2.4 and the comment claiming it enabled `app/global-not-found.tsx` was false. Measured here with the flag absent: 404 status **and** the custom localized copy, both in `pnpm dev` and against `pnpm build` + `pnpm start`, with an unchanged build route table. (When measuring this, check `lsof -nP -iTCP:<port> -sTCP:LISTEN` first — a lingering dev server serves the old config and hands you a confident wrong answer.)

**Amends ADR-0013**, which listed reliance on `experimental.globalNotFound` as an accepted trade-off. Everything else in ADR-0013 stands: `app/global-not-found.tsx` is still the right convention for this no-root-layout app, for the reasons given there — only the flag, and the trade-off it implied, are gone.

_Why:_ a template that ships a deprecated convention teaches it to every fork, and a config comment asserting something untrue is worse than no comment. _Trade-off:_ `proxy.ts` forecloses the `edge` runtime; if a fork needs it, the rename is what to revert.

_Superseded by ADR-0025: `proxy.ts`, `next.config.ts` and the Next conventions went with Next.js._

### ADR-0017 — Test-harness reliability over test-harness speed

**Accepted.** Four changes to the vitest/Playwright setup, each ported from a downstream fork that measured the failure first.

**`isolate: true` on the unit project** (was `false`). `isolate: false` shares one module registry across every file in a worker, so two files mocking the **same** module with different factories collide — whichever registered first wins for both. It only breaks once worker assignment puts the two files together, which is why it passes locally and fails in CI with a stack trace pointing into the _other_ file. `pool: "threads"` + `fileParallelism: true` stay; the isolation cost is small and the failure mode is not debuggable from the error.

**The `storybook` vitest project is gated behind `STORYBOOK_TEST`.** `storybookTest` loads Storybook's main config at **config** time, so every `vitest` invocation — including `--project=unit` — booted Storybook. Measured here: ~2.2s of config-load overhead on a run whose unit tests take 0.3s. `pnpm test:storybook` and `pnpm test:all` set the flag, so all three projects are still covered by one command; a bare `--project=storybook` without it simply won't find the project.

**Playwright local workers capped at 2** (`process.env.CI ? "50%" : 2`), reporter `dot` locally, and the dev server's `stdout`/`stderr` ignored outside CI. CI runs `pnpm start` — a production build, every route compiled — so it can use half the machine. A local run is `pnpm dev`, where Turbopack compiles each route on first hit; at Playwright's default (~5 workers) enough compiles are in flight that individual navigations stall past any assertion timeout. The symptom is a rotating cast of 1-4 failures per run, every one passing in isolation and none reproducible in a browser. Measured downstream: 5 workers → 2-4 failures every run; 2 workers → all green and _faster_ wall-clock, because the compiles stop fighting each other. **Raising assertion timeouts was tried first and does not fix it.**

**Integration runs reseed the database on teardown** — `src/core/test/integration-global.ts`, wired as `globalSetup` on the integration project, shelling out to a new `pnpm db:seed` (`scripts/seed.ts`, which applies `supabase/seed.sql` — the same file `supabase db reset` uses, so there is one seed source and not two). ADR-0016's global truncating `beforeEach` means a finished suite leaves the database **empty**, and the next thing to read it silently gets nothing: a dev server, an e2e run, or a `next build` that prerenders from `generateStaticParams` and exits 0 having prerendered almost nothing. A `globalSetup` **teardown** rather than a command chained after vitest in `package.json`, for two reasons: it runs whether the suite passed or failed — the failing run is exactly the one you want the database restored after — and it cannot mask vitest's exit code, which `vitest run …; pnpm db:seed` would, because a chained command's status becomes the script's. The seed must stay idempotent (delete-then-insert the rows it owns); nothing resets in front of it.

_Why:_ every one of these traded a small, predictable cost for a failure that is expensive precisely because it is intermittent and points somewhere else. _Trade-off:_ slightly slower unit startup, a flag to remember for Storybook tests, less local e2e parallelism, and one more `package.json` script.

_Superseded in part by ADR-0021: Playwright and the Storybook vitest project are removed, so the Playwright workers and `STORYBOOK_TEST` sections no longer apply. The seed file moved to `db/seed.sql`._

_Superseded in part by ADR-0025: the integration project and its reseeding teardown are removed with the database; the `isolate: true` section stands and now lives in `vite.config.ts`._

### ADR-0016 — Integration isolation is a global truncating `beforeEach`, not per-test `BEGIN`/`ROLLBACK`

**Accepted.** `src/core/test/db.ts` exposes `testDb` (a `max: 1` fixture connection, separate from the app's pool) and `resetDb()`, which TRUNCATEs every table in `@/db/schema`. `integration-setup.ts` registers it as a **global `beforeEach`**, so specs write no cleanup of their own. Replaces `withRollback` (ADR-0009), which is deleted.

_Why the rollback approach had to go:_ it pinned its own single connection, and the app's `@/db` client is a `max: 10` pool — so a `BEGIN`/`ROLLBACK` on the wrapper's connection isolates nothing the code under test does. Its own spec said as much and worked around it by asserting in raw SQL against the table, which meant the canonical integration example never exercised `listGuestbook`/`createGuestbookEntry` at all. Truncation isolates regardless of which connection the query landed on, so specs can call the real functions. `resetDb` also derives its table list from the schema, so adding a table can't silently leave it un-reset (and returns early when the schema is a bare placeholder, i.e. post-`pnpm eject:examples`).

_Cost accepted:_ TRUNCATE is slower than ROLLBACK and, unlike ROLLBACK, is **destructive if pointed at the wrong database** — so `db.ts` refuses any non-loopback host outright rather than pattern-matching known-remote hostnames. Revisit only if the suite needs `fileParallelism: true`, which would want a database-per-worker instead.

_Fixtures:_ row builders live with the feature they belong to (`src/features/<name>/__tests__/fixtures.ts`), insert through `testDb`, and default every column so a spec names only the values it asserts on. `insertGuestbookEntry` is the canonical example; keeping them feature-local means `pnpm eject:examples` removes them with the slice.

**Amends ADR-0009 / ADR-0012:** the barrel rule is unchanged, only the module it applies to — `@/test` still excludes the node-only member, now `@/test/db` instead of `@/test/withRollback`.

_Superseded by ADR-0025: the database, `src/core/test/db.ts` and the whole `*.spec.ts` integration project are removed. Reinstate this isolation model together with them if a server returns._

### ADR-0015 — The commit gate re-checks the command itself; the hook `if` filter is only an optimization

**Accepted.** `.claude/hooks/pre-commit.sh` re-derives whether the intercepted command is really a `git commit`, from the PreToolUse JSON payload on stdin, instead of trusting the `"if": "Bash(git commit *)"` filter in `.claude/settings.json`.

_Why:_ that filter fails **open** on shell compound constructs its parser can't decompose — a `for f in a b; do echo $f; done` matched nothing yet still fired the hook, so every such command paid a full typecheck + lint + format + unit run. Simple commands, pipelines and `&&` lists filter correctly; the compound forms are the leak. The `if` stays (it's a cheap first pass), but the script owns the decision.

_Direction of failure:_ no stdin (a human running the script from a terminal), no `jq`, or an unparseable payload all fall through to **running** the checks. A gate that skips when confused is worse than one that runs redundantly. The matcher is likewise deliberately loose — it tolerates an absolute `git` path and up to four global options (`git -C dir commit`, `git -c k=v commit`) — because a false positive costs one wasted check run while a false negative lets an ungated commit through. `set -e` also became `set -euo pipefail`, so an unset variable in the script fails loudly instead of gating on an empty string.

### ADR-0014 — `data-testid` is stripped by an SWC wasm plugin, gated on an explicit opt-in

**Accepted.** The portable test-id system (`src/core/test/ids`) puts a `data-testid` on every element e2e and Storybook select on, so those attributes reach the rendered output. They're stripped from the build by `@swc/plugin-react-remove-properties` loaded through `experimental.swcPlugins`.

_Why a wasm plugin and not `compiler.reactRemoveProperties`:_ that built-in option is **webpack-only** and Turbopack ignores it silently — no warning, no error, test ids simply still in the HTML. The wasm plugin is the same SWC transform, reachable from Turbopack. Its version is pinned to Next's own `swc_core` (Next 16.2.4 → `swc_core` v57 → plugin 12.6.0); a mismatch fails the build loudly, which is the failure mode we want. Bump both together.

_Why `STRIP_TEST_IDS`, not `NODE_ENV === "production"`:_ CI runs e2e against a **production** build (`pnpm start`), and every `*.e2e.ts` selects on `data-testid` — a `NODE_ENV` gate therefore breaks the e2e job, not the deploy. It is also not gated on a platform variable (`VERCEL_ENV` and friends): the template makes no assumption about where an app deploys, so the deploy that serves real users opts in explicitly. _Trade-off:_ default-off means a fork that never sets the variable ships its test ids — the safe direction, since the cost is a few bytes of attribute rather than a red CI suite or, worse, a green suite testing the wrong build.

_Superseded by ADR-0025: the SWC wasm plugin was Next/Turbopack-specific and is removed with it, as is `STRIP_TEST_IDS`. `data-testid` now ships in the bundle; the app is not deployed to users._

### ADR-0013 — Localized error boundaries + custom errors via next-intl

_Amended by ADR-0018: `experimental.globalNotFound` was measured to be a no-op on Next 16.2.4 and is gone from `next.config.ts`. `app/global-not-found.tsx` works without it; the "relies on the `experimental.globalNotFound` flag" trade-off below no longer applies. Everything else stands._

**Accepted.** The template ships the App Router error surface, all localized through next-intl, and demonstrates two kinds of "custom error" beyond built-in field validation. **Error boundaries — three files, each a different scope:** `[locale]/error.tsx` (Client Component — it takes `reset`; `useTranslations` works because it renders inside the layout's `NextIntlClientProvider`); `app/global-error.tsx` (root-layout errors); and `app/global-not-found.tsx` (unmatched routes). **Why `global-not-found`, not a `[locale]/not-found.tsx` + catch-all:** this app has no root `app/layout.tsx` — `[locale]/layout.tsx` is the effective root. Empirically (Next 16.2), an unmatched URL then never renders a route-segment `not-found.tsx`; Next drops it into the bare built-in `__next_error__` document (a root `not-found.tsx` can't help — it requires a root layout that doesn't exist). Next 16's `app/global-not-found.tsx` (enabled by `experimental.globalNotFound`) is built for exactly this: unmatched URLs are handled at the routing level, it renders its **own** `<html>`, and it explicitly needs no root layout. **The two `global-*` files share a constraint:** rendering outside the `[locale]` layout means no ambient provider and no request locale, so each stands up its own `NextIntlClientProvider` pinned to `routing.defaultLocale` with statically-imported messages — single-locale by construction, inherent to the position, not a shortcut. `global-error` is also kept dependency-light (plain `<button>`) as the catastrophic fallback. **Custom validation error:** the `guestbook` schema gains a `.refine` (no links) whose `custom` issue code maps to the `validation.custom` message key via the ADR-0008 `zodErrorMap`; wiring the map required dropping the schema's inline `.min` messages (an inline message is a per-issue override that beats the map). The map is passed per parse on **both** sides — server `safeParse(input, { error: zodErrorMap(t) })` and client `zodResolver(schema, { error: zodErrorMap(t) })`. **Custom domain error:** `GuestbookFormState` splits `fieldErrors` (per-field, Zod) from an optional `formError` typed code; the action wraps the write in try/catch and returns `formError: "unexpected"`, which the form maps to a translated `guestbook.errors.<code>` message — a server-decided error the input shape can't predict, distinct from field validation.

_Why:_ every real app needs localized error UI, and next-intl's error-file gotchas (client vs server boundary, the `global-*` files' missing provider, unmatched-route 404s in a no-root-layout app) are exactly the kind of thing an agent should inherit working rather than rediscover the hard way. Splitting field vs domain errors keeps validation and infrastructure failures in separate, individually-translatable channels. **Eject boundary:** the three error boundaries are **generic scaffolding** (not in the eject manifest's remove list, `errors` message namespace preserved) — they survive `pnpm eject:examples`; the guestbook-specific custom/domain-error wiring ejects with the slice. _Trade-off:_ the two `global-*` files are single-locale by construction; it relies on the `experimental.globalNotFound` flag (accepted — the alternative is the unstyled `__next_error__` document); and the single `validation.custom` key means all custom refinements in a schema share one message (a discriminator would need issue `params`, deferred as YAGNI).

_Superseded by ADR-0025: the App Router error conventions and next-intl are gone. One `src/app/ErrorBoundary.tsx` class component covers the SPA, with inline English copy._

### ADR-0012 — Barrels are homogeneous in reach-safety; `server-only` is the enforcement

**Accepted.** Generalizes the barrel/deep-import rules previously stated as one-offs in ADR-0007 (`@/supabase` split), ADR-0009 (`@/test` excludes `withRollback`), and ADR-0011 (feature client-safe barrel + deep `actions`/`queries`) into a single principle: **a barrel (`index.ts`) must be homogeneous in reach-safety** — everything it re-exports must be safe for _every_ consumer that imports the barrel. Two homogeneous kinds exist: **client-safe / isomorphic** barrels (`@/utils`, `@/hooks`, `@/i18n`, `@/features/<name>`), importable anywhere; and **server-only** barrels (`@/db`), fine because only server code imports them. What you must never do is **mix** client-safe and server-only members in one barrel a client can import — bundlers statically resolve the whole barrel graph, dragging server/node deps (postgres → `tls`/`net`) into the client bundle (the ADR-0009 failure). Members that pull server-only or node/test-heavy deps (`@/supabase/server`, `@/test/withRollback`, `@/test/render`, `@/features/*/{actions,queries}`) are therefore **direct imports**, off the client-safe barrel. One boundary, not a pile of exceptions.

**Enforcement is the `server-only` package, not convention.** Every server-only module imports `server-only`; via the `react-server` export condition it throws at build time if reached from a client bundle. With the guard universal, a mistaken barrel fails loudly and clearly instead of emitting broken client JS — so the direct-import rule is about ergonomics (honest import sites), not load-bearing for safety. `withRollback.ts` gained the guard here — it was the one server/node module missing it, which is exactly why ADR-0009 first surfaced as a cryptic `Can't resolve 'tls'`. Server Actions use `"use server"` (their own RPC boundary) and are treated as direct imports too: teaching "actions are RPC-safe but queries aren't" is subtle and bundler-dependent (Storybook's Vite doesn't honor `"use server"` like Next), so uniform direct-import is the simpler rule. `.server.ts`/`.client.ts` naming is **not** used — Next gives it no semantics (unlike Remix); role-named files (`server.ts`, `queries.ts`, `actions.ts`) plus the guard suffice. A per-feature `server/` subfolder (which would turn the boundary into a lint-able path) is the documented **scaling trigger** — adopt it when a feature accumulates enough server files to warrant it, not before.

_Why:_ collapses three ADR-era "exceptions" into one mental model, so contributors reason about a single boundary + a single enforcement mechanism rather than memorizing a list. _Trade-off:_ server/test-heavy members are always reached by direct path (no root-alias sugar), and the `server/`-folder path-lint is deferred, so today the client/server split is convention-guided but backstopped by the `server-only` build error.

_Superseded in part by ADR-0025: `server-only` and the server/client split went with Next.js. What stands is the rule behind it: a barrel never drags node-only or test-only dependencies into the app graph, and `@/test/render` stays a deep import._

### ADR-0011 — `src/features/` vertical-slice layer; feature-owned queries; layering enforced via oxlint

**Accepted.** Adds a fourth top-level `src/` folder, `features/`, for domain vertical slices. A feature (`src/features/<name>/`) owns its whole stack: client + presentational components, zod schema, stories, **Server Actions** (`actions.ts`), **data-access queries** (`queries.ts`), and co-located unit/integration/e2e tests. The `app/` route stays thin — it composes the feature and passes the action across the RSC boundary. The `guestbook` slice moved out of `src/components/guestbook` + `src/app/[locale]/guestbook` (route keeps only `page.tsx`); `src/components/` is now purely reusable (shadcn `ui/`). New alias: `@/features/*` → `src/features/*`.

**Feature has a client-safe barrel; server-only members are deep imports.** `src/features/<name>/index.ts` re-exports the client-safe surface (components, zod schema, and type-only re-exports of state/row types). It deliberately excludes `actions.ts` and `queries.ts` — both reach `@/db` → postgres, so re-exporting them would let a client bundle (or Storybook's Vite build) pull Node builtins in, the exact ADR-0009 failure. The route imports those two by direct path (`@/features/guestbook/{actions,queries}`). This is the **same shape as `@/supabase/client` vs `@/supabase/server` and `@/test` vs `@/test/withRollback`** — a public barrel with server-only members held out — so features are barrel-modules like `core/`, not an exception.

**Queries are feature-owned; `core/db` is client + schema only.** `listGuestbook`/`createGuestbookEntry` moved from `core/db/queries/` into `features/guestbook/queries.ts` (they are business logic, used only by the feature). The `core/db/queries/` directory is **removed**. `core/db` keeps the Drizzle client (`db`, server-only) and the **central schema** (the shared relational model, reached via `@/db`) — a feature query imports `{ db, <table> }` from `@/db`. Schema stays central deliberately: a Postgres/RLS app is inherently cross-cutting (FKs, RLS, join tables), `drizzle-kit generate` wants one schema source, and per-feature tables would force cross-feature imports the layering rule bans. `core/db/index.ts`'s `export *` forwarding is now eject-invariant, so it and the (removed) `queries/index.ts` drop out of the eject restore map.

**Layering is a DAG — `app → features → components → core`, imports point only down** — enforced by oxlint `no-restricted-imports` `patterns` in per-zone `.oxlintrc.json` `overrides`: `core/` imports none of the others; `components/` imports neither `app/`/`features/` **nor the data layer** (`@/db`, `@/supabase/server`) so reusable UI stays presentational and data-free; `features/` imports no `app/` and no other feature via `@/features/*` (intra-feature is relative). fallow boundary zones were considered (semantically ideal) but oxlint won: it already runs in the fast `pnpm check` + pre-commit gate, whereas `import/no-restricted-paths` (the zone rule) is unimplemented in oxc. Each override re-declares the react-memo `paths` ban because oxlint replaces (not merges) a rule's options per override.

_Why:_ the old split tied a "reusable" component to a route (`components/guestbook` imported a type from `app/.../actions`) — direction backwards. A feature layer gives each domain one home for its full stack, makes `components/`/`core/` genuinely reusable, and machine-checks the boundary instead of trusting convention. _Trade-off:_ a per-zone override block, and the DB relational model lives centrally while its queries live in features (a deliberate split — the model is shared, the access is feature-local); cross-feature isolation is enforced via the `@/features/*` ban, but intra-feature relative imports are unchecked, and "only `queries.ts` may touch the raw `db` client" is convention, not linted (oxlint globs can't express the negation).

_Amended by ADR-0025: features own their data access as `fetch` wrappers instead of server queries and actions; the layering and its oxlint enforcement stand._

### ADR-0010 — Canonical example slice, replaced-not-deleted; `pnpm eject:examples`

**Accepted.** The template ships one interlocking `guestbook` slice exemplifying every core feature pattern: Drizzle table + companion RLS migration, server-only data-access fns, a Server Action (react-hook-form + zod + `useActionState`), a feature RSC + presentational list, the first testid `T` tree, the first `withRollback` integration test and `loc()` e2e, and an `/api/health` Route Handler. Examples are **intentional best-practice references an agent inherits in context**. When building a real feature, an agent **re-points** the pattern — replaces the example's usage with the real one — rather than deleting it, so the pattern is never lost, only re-aimed. For a fresh app with no use for the demo, `pnpm eject:examples` strips the whole slice back to a bare skeleton (`--clean-self` also removes the eject machinery). The slice wires into a few shared files (the `db`/`test` barrels, `messages/en.json`) via re-exports; eject reverts those from committed pristine snapshots under `scripts/eject/`, drops the `guestbook` i18n key, and removes generated artifacts (migrations, `supabase-types.ts`). Correctness gate: a worktree run of eject must leave `pnpm check` + `pnpm build` green.

_Why:_ a fork (agent or human) gets a working, best-practice reference for each pattern instead of a blank slate, plus a one-command path back to bare when the demo isn't wanted. _Trade-off:_ the slice must stay wired through a small, documented set of shared files so eject remains a mechanical manifest operation.

_Superseded by ADR-0020: the `guestbook` slice and `pnpm eject:examples` were removed when the app became `fintechers-aml`; the first real feature is `src/features/review-queue/`._

### ADR-0009 — `@/test` barrel excludes `withRollback` (second no-barrel exception)

_Amended by ADR-0016: `withRollback` was replaced by `@/test/db`; the barrel rule below is unchanged, only the module it names._

**Accepted.** `src/core/test/index.ts` re-exports `loc` and `T` but **not** `withRollback`. The guestbook e2e (Task 9) was the first thing to load a page using the `@/test` barrel from a real Next.js dev bundle — `GuestbookForm` (a Client Component) imports `T` from `@/test`, and webpack statically resolves every module reachable from that barrel, including `withRollback`'s `await import("postgres")`. `postgres` needs Node builtins (`tls`, `net`, …) with no browser shim, so the dev server 500'd (`Module not found: Can't resolve 'tls'`) on `/guestbook`, timing out the e2e's `fill()` calls. Lazily importing `postgres` inside `withRollback` (ADR-adjacent fix in an earlier task) wasn't enough — webpack still resolves a dynamic import's target for chunking even if it never executes client-side. Fix: drop `withRollback` from the barrel; integration tests import it via the deep alias, `@/test/withRollback`, same shape as the `supabase` exception below. This amends ADR-0007's "supabase is the one exception" — read it as two exceptions now.

_Why:_ keeps `@/test`'s root barrel genuinely browser-safe for `T`/`loc` consumers without giving up the deep-import escape hatch for the node-only test helper. _Trade-off:_ `withRollback` callers must know to reach past the barrel — same trade-off already accepted for `supabase`.

_Superseded in part by ADR-0021: the `@/test` root barrel is removed with `loc`; every `@/test` member is a deep import._

### ADR-0008 — Zod message i18n: per-parse next-intl error map, Zod default fallback

**Accepted.** Localize Zod v4 validation messages through a small per-parse error map (`@/validation` → `zodErrorMap(t)`), **never** a global `z.config()`. Defaults stay Zod's built-in (English); a `validation` message namespace whose keys mirror Zod's issue taxonomy overrides only the codes it defines, and any untranslated code returns `undefined` to fall through to Zod's default. Wire it per parse at each boundary — `schema.safeParse(input, { error: zodErrorMap(t) })`, or `zodResolver(schema, { error: zodErrorMap(t) })` on the client. Keys are derived from the issue by convention (`too_small.<origin>`, `invalid_format.<format>`, missing field → `required`), so the mapping lives in the message catalog, not in code.

_Why:_ `z.config()` mutates module-global state, which races across concurrent RSC / Server Action requests; a per-parse map carries no shared state and is safe under Next.js concurrency, server and client. Extends ADR-0005 (writes via Server Actions + `react-hook-form` + `zod`). _Trade-off:_ callers pass the map explicitly at each parse site (vs. a one-time global), and one documented cast bridges next-intl's statically-typed keys to runtime-derived ones.

_Superseded by ADR-0025: with i18n removed there is no translator to back the map; `@/validation` is deleted and Zod's English defaults stand. The per-parse (never `z.config()`) rule still applies if message overrides come back._

### ADR-0007 — `src/core/` for shared infrastructure; bare per-module aliases

**Accepted.** All cross-cutting infrastructure lives in `src/core/`, **one module per concern** — a folder with a deliberate `index.ts` public API (`db/`, `hooks/`, `i18n/`, `supabase/`, `test/` incl. `test/ids/`, `utils/`), or a flat `<name>.ts` for a single cohesive file that won't grow (`env.ts`). Both resolve through the same bare alias. Top-level `src/` is therefore exactly `app/`, `components/`, `core/`, `docs/`, plus `middleware.ts` (Next.js only auto-discovers it at `src/middleware.ts`). Consolidated from the prior `src/{db,test,lib,testids}` layout; the 1-line `src/i18n.ts` next-intl shim was deleted (`next.config.ts` points the plugin at `src/core/i18n/request.ts`).

Each core module gets a **bare alias** in `tsconfig.json` `paths` — `@/db`, `@/env`, `@/hooks`, `@/i18n`, `@/test`, `@/utils` — while `@/*` → `src/*` covers `@/app`/`@/components`/`@/middleware`. Consumers import only through the root alias (`import { cn } from "@/utils"`), never `@/core/…` or a deep internal path; `index.ts` files name exports explicitly (no `export *` grab-bags). `supabase` is the one exception — it has **no** root index because `server.ts` is `server-only`, so callers import `@/supabase/client` or `@/supabase/server` to keep server-only code out of client bundles. **Amended by ADR-0009:** `@/test` is a second exception (excludes `withRollback` from its barrel for the same client-bundle reason). **Amended by ADR-0011:** `src/` now also contains `features/` (vertical slices); that layer is intentionally non-barreled — features are imported by direct path, not a root alias.

_Why:_ one obvious home for infrastructure; fewer top-level folders; uniform short imports; and the bare alias decouples the import path from the physical location, so moving a module within `core` doesn't churn every importer. _Trade-off:_ a `paths` entry per core module, and a one-time mechanical import rewrite.

_Superseded in part by ADR-0021: `src/core/supabase` and its aliases are removed._

### ADR-0006 — Commit-quality gate via Claude PreToolUse hook; husky dropped

**Accepted.** Removed husky (+ the `prepare` script and `.husky/`). The gate (`.claude/hooks/pre-commit.sh` — typecheck + lint + format:check + changed unit tests) now runs as a Claude **PreToolUse** hook on `Bash(git commit *)`: it blocks the commit (exit 2) on failure and feeds the output back to the agent. _Why:_ commits are largely agent-driven, so a tool-agnostic git hook earned little; this keeps one hook system (`.claude/`), drops a dependency + `prepare` step, and gives the agent inline failure output. CI remains the backstop for non-agent commits. _Trade-off:_ commits made outside a Claude session (human terminal/IDE) are no longer gated locally — accepted, since CI still gates them.

### ADR-0005 — Data fetching: RSC + Server Actions; no client query lib, no axios

**Accepted.** Reads via Server Components calling `src/db` service functions; list state (pagination/filters/sort) via URL `searchParams`. Writes via Server Actions + `react-hook-form` + `zod`; cache invalidation via `revalidateTag`/`revalidatePath`; optimistic UX via `useOptimistic`/`useActionState`; realtime via the Supabase Realtime browser channel. **No TanStack Query / SWR globally** — RSC + React 19 already own caching/dedup/invalidation; adopt locally only for a proven client-cache-heavy surface (YAGNI trigger, not a foundation choice). Native `fetch` for server-side external calls; **no axios/ky/ofetch**. _Why:_ leverage the framework fully, one source of truth, smallest bundle.

_Superseded by ADR-0025 for the frontend: there is no server in a client-only SPA, so reads and writes go to the Kotlin engine (ADR-0024) over `fetch`. The "no client query lib, no axios" position stands._

### ADR-0004 — Canonical specs committed in `docs/`; drafts stay out of git

**Accepted.** Canonical architecture and foundation specs live committed under `docs/` so a fresh clone / CI / cloud agent always has them. Working drafts and plans-under-review stay out of git (gitignored). _Why:_ reproducibility for autonomous agents, while keeping half-baked drafts out of the history.

### ADR-0003 — dex for live task memory; ROADMAP/CHANGELOG/DECISIONS as files

**Accepted.** Live tasks/progress/next-steps/issues are tracked in **dex** (`.dex/` JSONL), not hand-rolled `PROGRESS.md`/`ISSUES.md`. Durable narrative (roadmap, releases, decisions) stays as committed markdown. _Why:_ dex already does multi-session task memory with rich context and conflict-free merges; don't rebuild it. dex task IDs are never referenced in commits/PRs (ephemeral).

_Superseded by ADR-0030: dex was never used here and is removed._

### ADR-0002 — React Compiler; ban `useMemo`/`useCallback`/`memo`

**Accepted.** React Compiler handles memoisation; `no-restricted-imports` blocks manual memo hooks. _Why:_ removes a class of stale-dependency bugs and noisy code; the compiler is more reliable than hand-tuning.

### ADR-0001 — oxlint + oxfmt over ESLint + Prettier

**Accepted.** Lint via **oxlint** (config in `.oxlintrc.json`) + format via **oxfmt**, instead of ESLint + Prettier. _Why:_ speed and a single Rust-based toolchain; the agent-critical rules (`max-params: 3`, `complexity: 15`, import hygiene) are configured equivalently.
