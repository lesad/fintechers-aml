# Decisions (ADRs)

> **Intended use:** an append-only log of architecture decisions. Add a new ADR whenever a non-obvious call is made. **Never edit an accepted ADR** — supersede it with a new one and annotate the old (`Superseded by ADR-NNNN`). Newest first. Keep entries short: the decision, its status, and _why_.

### ADR-0033 — Triage is a deterministic pure function over an alert; config is versioned data

**Accepted.** Implements ADR-0032's "triage is code" for the engine. Every alert gets a disposition — `AUTO_CLOSE`, `REVIEW_LOW`, `REVIEW_MEDIUM`, `REVIEW_HIGH`, `ESCALATE` — from `Triage.decide(input, config)` in `engine/.../triage/`, a pure function with no clock, no connection, no model and no randomness. Six steps in a fixed order: base score per rule key, risk factors, score-to-band, the auto-close gate, the missing-data floor, then the hard floors. A floor is applied with `maxOf` over the enum ordinal, so it can only ever make an outcome stricter. Everything time-shaped arrives on the input (`asOf` is the run period's end, never `now()`); money stays `Long` haléře and `CanonicalJson` throws if a float reaches the input hash.

**One scale, not two.** ADR-0032 describes triage as `FP`/`REVIEW` plus a separate priority scorecard; this collapses both into a single ordered disposition with the score attached. `AUTO_CLOSE` is the old `FP`, and the three `REVIEW_*` levels carry what the scorecard's bands carried. _Why the change:_ two numbers that can disagree (a `FP` with a high priority) need a tie-break rule nobody had written, and the floors — the part a regulator actually asks about — only make sense against one ordered scale. The scorecard's factor vocabulary (rating, PEP, country, amount, tenure, channel, multiple flags) is kept as the risk factors.

Tuning lives in `resources/triage/triage-config-v1.json` under a `configVersion`, validated on load. Changing a number means a new file and a new version, so decisions already taken stay explicable under the config that produced them. Each decision stores its reasons, `config_version` and a SHA-256 `input_hash` over a canonical serialisation, in `alert_triage` — a separate table, so a run can be re-triaged (`bootRun --args=triage`) without touching detection output.

_Why:_ an AML disposition has to be defensible to a regulator line by line, which rules out a model and rules out hidden state; the hash plus the config version make any past decision reproducible. _Trade-off:_ the weights are a judgement call, not a fit — the data carries no labels — so they are data rather than code, and expected to be re-tuned. Supersedes the paper scorecard in `docs/rules/priority.md`.

### ADR-0032 — Triage is code; AI only writes summaries and rule proposals; `docs/rules/` follows the engine

**Accepted.** No model takes part in detection, triage, priority or routing. Triage is code: guardrails and a policy over the alert's evidence and the client's fields give `FP` or `REVIEW`, and a scorecard gives the priority. AI does two things: it writes a summary for the reviewer from `llm_context` and the log, and it drafts rule proposals that go through the engine's checks, backtest and approval like any other rule version. The engine owns detection (alert types, rules, grains, variables, parameter names and units, layers, versions, runs, hits, evidence); `docs/rules/` cites it and owns only the interpretation decisions and the second layer (guardrails, triage, priority, route, reason, log, and what `llm_context` must carry). `docs/rules/` is organised by alert type, not by rule, because rules are configured at runtime; triage reads each alert type's evidence contract, never a specific rule key. Terms: `docs/GLOSSARY.md`. _Why:_ triage is graded on correctness and must be reproducible and explainable from the evidence alone; a model in the decision path adds neither, and the data run found no behavioural signal a model could add beyond the computed gaps. _Trade-off:_ the Jev questions in `docs/rules/` are dropped, and with them the typed-judgement pitch. Supersedes the Jev part of ADR-0020 and the Jev rows of the split in `docs/challenge/decision-architecture.md`.

### ADR-0031 — Component variants through `cva` (class-variance-authority)

**Accepted.** Classes that depend on props or state are declared with `cva` from class-variance-authority, as named variants (`level`, `active`, `embedded`, `state`…) with `compoundVariants` where two props combine, instead of inline ternaries and string concatenation. `cn()` stays for merging a caller's `className` on top. Applies in `components/` and in features (`RiskBadge`, `StatusLabel`, `Tab`, `Table`, `Card`, the decision buttons, the money-flow ribbons). _Why:_ the team asked for it once the first components multiplied their conditional classes; variants give each visual state a name, keep Tailwind classes greppable, and are the pattern most Tailwind codebases use. Re-adds the `class-variance-authority` dependency that ADR-0028 removed with shadcn/ui; the rest of ADR-0028 (no component library) stands.

### ADR-0022 — Short-lived PRs, gated by CI only, merged by auto-merge (superseded by ADR-0026)

**Accepted.** All work reaches `main` through a PR that GitHub squash-merges on its own once the `check`, `integration` and `build` jobs pass. The `main` ruleset (`.github/rulesets/main.json`) requires a PR with 0 approvals, squash only, and blocks force-push and deletion; the repo admin can bypass. Branches need not be up to date with `main` before merging. `pnpm ship` (`scripts/ship.sh`) pushes, opens the PR, arms auto-merge and waits on the checks, printing the failing log on red. CI cancels stale PR runs and caps each job at 10 minutes. _Why:_ the team and its agents work from the CLI only and need to move fast before the freeze; CI is the quality gate, and the PRs give the judges a readable history. A merge queue would catch two green PRs that break together, but it needs an organisation-owned repo; CI on `main` catches that case after the fact.

### ADR-0019 — Lint policy: `type` over `interface`, PascalCase component files, and the test-relaxation block covers every test suffix

**Accepted.** Three `.oxlintrc.json` changes, ported from a downstream fork that had hit each of them.

**`typescript/consistent-type-definitions: ["error", "type"]`.** One way to declare an object shape, so an agent never has to pick. Exactly one exemption — `global.ts`, because module augmentation (`declare module "next-intl" { interface AppConfig … }`) cannot use a `type` alias — plus `src/components/ui/**` (shadcn output, below). `src/core/test/ids/tree.ts`'s `TestIdNode` was the only production `interface`; converting it **widened** one cast rather than removing it (`Object.entries` on a `type` widens the value to the union of the declared members, which doesn't overlap `TestIdNode`, so the assertion must route via `unknown`) — the trade accepted for the single-form rule.

**PascalCase component filenames** — `unicorn/filename-case: pascalCase`, scoped to `.tsx` files under `src/components/`. Component files are named for the component they export. The shadcn `ui/` folder is exempt: it generates kebab-case and `pnpm dlx shadcn add` must stay a no-edit operation; the same block also exempts `consistent-type-definitions`, `jsx-a11y/label-has-associated-control` and `react/no-array-index-key`, all shadcn-upstream conventions. That block must stay **last** in `overrides` — oxlint applies overrides in order and the later match wins per rule, so an exemption placed before the rule that grants it is silently dead. Everything under `src/features/` keeps kebab-case: the rule is scoped to the reusable layer, where one file = one exported component actually holds.

**The relaxation block now lists `*.spec` and `*.e2e`, not just `*.test`.** It had covered `*.test`/`*.stories`/`tests/**`/`src/core/test/**`, so this repo's own integration specs and Playwright tests were held to production rules — an oversight, not a policy. `no-await-in-loop` is off there too: sequential awaits are the normal shape of a spec.

_Why:_ each was a real papercut downstream, and lint config is exactly the kind of thing a template should get right once. _Trade-off:_ the `unknown`-routed cast in `tree.ts`, and a per-zone override ordering constraint that is invisible in the file itself (hence the comment on the last block — oxlint parses JSONC, so `//` comments are legal there).

_Superseded in part by ADR-0028: shadcn/ui and its `src/components/ui/**` exemptions are removed._

### ADR-0018 — Track Next 16's stable conventions: `proxy.ts`, top-level `typedRoutes`, no `globalNotFound` flag

**Accepted.** Three corrections where `next.config.ts`/`src/` had drifted behind what Next 16.2.4 actually does.

**`src/middleware.ts` → `src/proxy.ts`** (default export renamed `middleware` → `proxy`, `src/middleware.test.ts` → `src/proxy.test.ts`). Next 16 renamed the file convention; the old name still works but emits a build-time deprecation (`warnOnce`, with a `@next/codemod middleware-to-proxy`), and `next build`'s output already labels the entry `ƒ Proxy (Middleware)`. The one constraint that mattered: **the `proxy` runtime is always `nodejs` and cannot be configured** — no problem here, since both things the file does (next-intl's middleware and the Supabase `updateSession` refresh) run on node. An app that needs the `edge` runtime must stay on `middleware.ts`. `@/supabase/middleware` keeps its name — it's our own helper, not the Next convention.

**`typedRoutes` moved out of `experimental`** — stable in Next 16.

**`experimental.globalNotFound` dropped.** The flag was a **no-op** on 16.2.4 and the comment claiming it enabled `app/global-not-found.tsx` was false. Measured here with the flag absent: 404 status **and** the custom localized copy, both in `pnpm dev` and against `pnpm build` + `pnpm start`, with an unchanged build route table. (When measuring this, check `lsof -nP -iTCP:<port> -sTCP:LISTEN` first — a lingering dev server serves the old config and hands you a confident wrong answer.)

**Amends ADR-0013**, which listed reliance on `experimental.globalNotFound` as an accepted trade-off. Everything else in ADR-0013 stands: `app/global-not-found.tsx` is still the right convention for this no-root-layout app, for the reasons given there — only the flag, and the trade-off it implied, are gone.

_Why:_ a template that ships a deprecated convention teaches it to every fork, and a config comment asserting something untrue is worse than no comment. _Trade-off:_ `proxy.ts` forecloses the `edge` runtime; if a fork needs it, the rename is what to revert.

_Superseded by ADR-0025: `proxy.ts`, `next.config.ts` and the Next conventions went with Next.js._

### ADR-0017 — Test-harness reliability over test-harness speed

**Accepted.** Four changes to the vitest/Playwright setup, each ported from a downstream fork that measured the failure first.

**`isolate: true` on the unit project** (was `false`). `isolate: false` shares one module registry across every file in a worker, so two files mocking the **same** module with different factories collide — whichever registered first wins for both. It only breaks once worker assignment puts the two files together, which is why it passes locally and fails in CI with a stack trace pointing into the _other_ file. `pool: "threads"` + `fileParallelism: true` stay; the isolation cost is small and the failure mode is not debuggable from the error.

**The `storybook` vitest project is gated behind `STORYBOOK_TEST`.** `storybookTest` loads Storybook's main config at **config** time, so every `vitest` invocation — including `--project=unit` — booted Storybook. Measured here: ~2.2s of config-load overhead on a run whose unit tests take 0.3s. `pnpm test:storybook` and `pnpm test:all` set the flag, so all three projects are still covered by one command; a bare `--project=storybook` without it simply won't find the project.

**Playwright local workers capped at 2** (`process.env.CI ? "50%" : 2`), reporter `dot` locally, and the dev server's `stdout`/`stderr` ignored outside CI. CI runs `pnpm start` — a production build, every route compiled — so it can use half the machine. A local run is `pnpm dev`, where Turbopack compiles each route on first hit; at Playwright's default (~5 workers) enough compiles are in flight that individual navigations stall past any assertion timeout. The symptom is a rotating cast of 1-4 failures per run, every one passing in isolation and none reproducible in a browser. Measured downstream: 5 workers → 2-4 failures every run; 2 workers → all green and _faster_ wall-clock, because the compiles stop fighting each other. **Raising assertion timeouts was tried first and does not fix it.**

**Integration runs reseed the database on teardown** — `src/core/test/integration-global.ts`, wired as `globalSetup` on the integration project, shelling out to a new `pnpm db:seed` (`scripts/seed.ts`, which applies `supabase/seed.sql` — the same file `supabase db reset` uses, so there is one seed source and not two). ADR-0016's global truncating `beforeEach` means a finished suite leaves the database **empty**, and the next thing to read it silently gets nothing: a dev server, an e2e run, or a `next build` that prerenders from `generateStaticParams` and exits 0 having prerendered almost nothing. A `globalSetup` **teardown** rather than a command chained after vitest in `package.json`, for two reasons: it runs whether the suite passed or failed — the failing run is exactly the one you want the database restored after — and it cannot mask vitest's exit code, which `vitest run …; pnpm db:seed` would, because a chained command's status becomes the script's. The seed must stay idempotent (delete-then-insert the rows it owns); nothing resets in front of it.

_Why:_ every one of these traded a small, predictable cost for a failure that is expensive precisely because it is intermittent and points somewhere else. _Trade-off:_ slightly slower unit startup, a flag to remember for Storybook tests, less local e2e parallelism, and one more `package.json` script.

_Superseded in part by ADR-0021: Playwright and the Storybook vitest project are removed, so the Playwright workers and `STORYBOOK_TEST` sections no longer apply. The seed file moved to `db/seed.sql`._

_Superseded in part by ADR-0025: the integration project and its reseeding teardown are removed with the database; the `isolate: true` section stands and now lives in `vite.config.ts`._

### ADR-0016 — Integration isolation is a global truncating `beforeEach`, not per-test `BEGIN`/`ROLLBACK`

**Accepted.** `src/core/test/db.ts` exposes `testDb` (a `max: 1` fixture connection, separate from the app's pool) and `resetDb()`, which TRUNCATEs every table in `@/db/schema`. `integration-setup.ts` registers it as a **global `beforeEach`**, so specs write no cleanup of their own. Replaces `withRollback` (ADR-0009), which is deleted.

_Why the rollback approach had to go:_ it pinned its own single connection, and the app's `@/db` client is a `max: 10` pool — so a `BEGIN`/`ROLLBACK` on the wrapper's connection isolates nothing the code under test does. Its own spec said as much and worked around it by asserting in raw SQL against the table, which meant the canonical integration example never exercised `listGuestbook`/`createGuestbookEntry` at all. Truncation isolates regardless of which connection the query landed on, so specs can call the real functions. `resetDb` also derives its table list from the schema, so adding a table can't silently leave it un-reset (and returns early when the schema is a bare placeholder, i.e. post-`pnpm eject:examples`).

_Cost accepted:_ TRUNCATE is slower than ROLLBACK and, unlike ROLLBACK, is **destructive if pointed at the wrong database** — so `db.ts` refuses any non-loopback host outright rather than pattern-matching known-remote hostnames. Revisit only if the suite needs `fileParallelism: true`, which would want a database-per-worker instead.

_Fixtures:_ row builders live with the feature they belong to (`src/features/<name>/__tests__/fixtures.ts`), insert through `testDb`, and default every column so a spec names only the values it asserts on. `insertGuestbookEntry` is the canonical example; keeping them feature-local means `pnpm eject:examples` removes them with the slice.

**Amends ADR-0009 / ADR-0012:** the barrel rule is unchanged, only the module it applies to — `@/test` still excludes the node-only member, now `@/test/db` instead of `@/test/withRollback`.

_Superseded by ADR-0025: the database, `src/core/test/db.ts` and the whole `*.spec.ts` integration project are removed. Reinstate this isolation model together with them if a server returns._

### ADR-0015 — The commit gate re-checks the command itself; the hook `if` filter is only an optimization

**Accepted.** `.claude/hooks/pre-commit.sh` re-derives whether the intercepted command is really a `git commit`, from the PreToolUse JSON payload on stdin, instead of trusting the `"if": "Bash(git commit *)"` filter in `.claude/settings.json`.

_Why:_ that filter fails **open** on shell compound constructs its parser can't decompose — a `for f in a b; do echo $f; done` matched nothing yet still fired the hook, so every such command paid a full typecheck + lint + format + unit run. Simple commands, pipelines and `&&` lists filter correctly; the compound forms are the leak. The `if` stays (it's a cheap first pass), but the script owns the decision.

_Direction of failure:_ no stdin (a human running the script from a terminal), no `jq`, or an unparseable payload all fall through to **running** the checks. A gate that skips when confused is worse than one that runs redundantly. The matcher is likewise deliberately loose — it tolerates an absolute `git` path and up to four global options (`git -C dir commit`, `git -c k=v commit`) — because a false positive costs one wasted check run while a false negative lets an ungated commit through. `set -e` also became `set -euo pipefail`, so an unset variable in the script fails loudly instead of gating on an empty string.

### ADR-0014 — `data-testid` is stripped by an SWC wasm plugin, gated on an explicit opt-in

**Accepted.** The portable test-id system (`src/core/test/ids`) puts a `data-testid` on every element e2e and Storybook select on, so those attributes reach the rendered output. They're stripped from the build by `@swc/plugin-react-remove-properties` loaded through `experimental.swcPlugins`.

_Why a wasm plugin and not `compiler.reactRemoveProperties`:_ that built-in option is **webpack-only** and Turbopack ignores it silently — no warning, no error, test ids simply still in the HTML. The wasm plugin is the same SWC transform, reachable from Turbopack. Its version is pinned to Next's own `swc_core` (Next 16.2.4 → `swc_core` v57 → plugin 12.6.0); a mismatch fails the build loudly, which is the failure mode we want. Bump both together.

_Why `STRIP_TEST_IDS`, not `NODE_ENV === "production"`:_ CI runs e2e against a **production** build (`pnpm start`), and every `*.e2e.ts` selects on `data-testid` — a `NODE_ENV` gate therefore breaks the e2e job, not the deploy. It is also not gated on a platform variable (`VERCEL_ENV` and friends): the template makes no assumption about where an app deploys, so the deploy that serves real users opts in explicitly. _Trade-off:_ default-off means a fork that never sets the variable ships its test ids — the safe direction, since the cost is a few bytes of attribute rather than a red CI suite or, worse, a green suite testing the wrong build.

_Superseded by ADR-0025: the SWC wasm plugin was Next/Turbopack-specific and is removed with it, as is `STRIP_TEST_IDS`. `data-testid` now ships in the bundle; the app is not deployed to users._

### ADR-0013 — Localized error boundaries + custom errors via next-intl

_Amended by ADR-0018: `experimental.globalNotFound` was measured to be a no-op on Next 16.2.4 and is gone from `next.config.ts`. `app/global-not-found.tsx` works without it; the "relies on the `experimental.globalNotFound` flag" trade-off below no longer applies. Everything else stands._

**Accepted.** The template ships the App Router error surface, all localized through next-intl, and demonstrates two kinds of "custom error" beyond built-in field validation. **Error boundaries — three files, each a different scope:** `[locale]/error.tsx` (Client Component — it takes `reset`; `useTranslations` works because it renders inside the layout's `NextIntlClientProvider`); `app/global-error.tsx` (root-layout errors); and `app/global-not-found.tsx` (unmatched routes). **Why `global-not-found`, not a `[locale]/not-found.tsx` + catch-all:** this app has no root `app/layout.tsx` — `[locale]/layout.tsx` is the effective root. Empirically (Next 16.2), an unmatched URL then never renders a route-segment `not-found.tsx`; Next drops it into the bare built-in `__next_error__` document (a root `not-found.tsx` can't help — it requires a root layout that doesn't exist). Next 16's `app/global-not-found.tsx` (enabled by `experimental.globalNotFound`) is built for exactly this: unmatched URLs are handled at the routing level, it renders its **own** `<html>`, and it explicitly needs no root layout. **The two `global-*` files share a constraint:** rendering outside the `[locale]` layout means no ambient provider and no request locale, so each stands up its own `NextIntlClientProvider` pinned to `routing.defaultLocale` with statically-imported messages — single-locale by construction, inherent to the position, not a shortcut. `global-error` is also kept dependency-light (plain `<button>`) as the catastrophic fallback. **Custom validation error:** the `guestbook` schema gains a `.refine` (no links) whose `custom` issue code maps to the `validation.custom` message key via the ADR-0008 `zodErrorMap`; wiring the map required dropping the schema's inline `.min` messages (an inline message is a per-issue override that beats the map). The map is passed per parse on **both** sides — server `safeParse(input, { error: zodErrorMap(t) })` and client `zodResolver(schema, { error: zodErrorMap(t) })`. **Custom domain error:** `GuestbookFormState` splits `fieldErrors` (per-field, Zod) from an optional `formError` typed code; the action wraps the write in try/catch and returns `formError: "unexpected"`, which the form maps to a translated `guestbook.errors.<code>` message — a server-decided error the input shape can't predict, distinct from field validation.

_Why:_ every real app needs localized error UI, and next-intl's error-file gotchas (client vs server boundary, the `global-*` files' missing provider, unmatched-route 404s in a no-root-layout app) are exactly the kind of thing an agent should inherit working rather than rediscover the hard way. Splitting field vs domain errors keeps validation and infrastructure failures in separate, individually-translatable channels. **Eject boundary:** the three error boundaries are **generic scaffolding** (not in the eject manifest's remove list, `errors` message namespace preserved) — they survive `pnpm eject:examples`; the guestbook-specific custom/domain-error wiring ejects with the slice. _Trade-off:_ the two `global-*` files are single-locale by construction; it relies on the `experimental.globalNotFound` flag (accepted — the alternative is the unstyled `__next_error__` document); and the single `validation.custom` key means all custom refinements in a schema share one message (a discriminator would need issue `params`, deferred as YAGNI).

_Superseded by ADR-0025: the App Router error conventions and next-intl are gone. One `src/app/ErrorBoundary.tsx` class component covers the SPA, with inline English copy._

### ADR-0012 — Barrels are homogeneous in reach-safety; `server-only` is the enforcement

**Accepted.** Generalizes the barrel/deep-import rules previously stated as one-offs in ADR-0007 (`@/supabase` split), ADR-0009 (`@/test` excludes `withRollback`), and ADR-0011 (feature client-safe barrel + deep `actions`/`queries`) into a single principle: **a barrel (`index.ts`) must be homogeneous in reach-safety** — everything it re-exports must be safe for _every_ consumer that imports the barrel. Two homogeneous kinds exist: **client-safe / isomorphic** barrels (`@/utils`, `@/hooks`, `@/i18n`, `@/features/<name>`), importable anywhere; and **server-only** barrels (`@/db`), fine because only server code imports them. What you must never do is **mix** client-safe and server-only members in one barrel a client can import — bundlers statically resolve the whole barrel graph, dragging server/node deps (postgres → `tls`/`net`) into the client bundle (the ADR-0009 failure). Members that pull server-only or node/test-heavy deps (`@/supabase/server`, `@/test/withRollback`, `@/test/render`, `@/features/*/{actions,queries}`) are therefore **direct imports**, off the client-safe barrel. One boundary, not a pile of exceptions.

**Enforcement is the `server-only` package, not convention.** Every server-only module imports `server-only`; via the `react-server` export condition it throws at build time if reached from a client bundle. With the guard universal, a mistaken barrel fails loudly and clearly instead of emitting broken client JS — so the direct-import rule is about ergonomics (honest import sites), not load-bearing for safety. `withRollback.ts` gained the guard here — it was the one server/node module missing it, which is exactly why ADR-0009 first surfaced as a cryptic `Can't resolve 'tls'`. Server Actions use `"use server"` (their own RPC boundary) and are treated as direct imports too: teaching "actions are RPC-safe but queries aren't" is subtle and bundler-dependent (Storybook's Vite doesn't honor `"use server"` like Next), so uniform direct-import is the simpler rule. `.server.ts`/`.client.ts` naming is **not** used — Next gives it no semantics (unlike Remix); role-named files (`server.ts`, `queries.ts`, `actions.ts`) plus the guard suffice. A per-feature `server/` subfolder (which would turn the boundary into a lint-able path) is the documented **scaling trigger** — adopt it when a feature accumulates enough server files to warrant it, not before.

_Why:_ collapses three ADR-era "exceptions" into one mental model, so contributors reason about a single boundary + a single enforcement mechanism rather than memorizing a list. _Trade-off:_ server/test-heavy members are always reached by direct path (no root-alias sugar), and the `server/`-folder path-lint is deferred, so today the client/server split is convention-guided but backstopped by the `server-only` build error.

_Superseded in part by ADR-0025: `server-only` and the server/client split went with Next.js. What stands is the rule behind it: a barrel never drags node-only or test-only dependencies into the app graph, and `@/test/render` stays a deep import._

### ADR-0011 — `src/features/` vertical-slice layer; feature-owned queries; layering enforced via oxlint

**Accepted.** Adds a fourth top-level `src/` folder, `features/`, for domain vertical slices. A feature (`src/features/<name>/`) owns its whole stack: client + presentational components, zod schema, stories, **Server Actions** (`actions.ts`), **data-access queries** (`queries.ts`), and co-located unit/integration/e2e tests. The `app/` route stays thin — it composes the feature and passes the action across the RSC boundary. The `guestbook` slice moved out of `src/components/guestbook` + `src/app/[locale]/guestbook` (route keeps only `page.tsx`); `src/components/` is now purely reusable (shadcn `ui/`). New alias: `@/features/*` → `src/features/*`.

**Feature has a client-safe barrel; server-only members are deep imports.** `src/features/<name>/index.ts` re-exports the client-safe surface (components, zod schema, and type-only re-exports of state/row types). It deliberately excludes `actions.ts` and `queries.ts` — both reach `@/db` → postgres, so re-exporting them would let a client bundle (or Storybook's Vite build) pull Node builtins in, the exact ADR-0009 failure. The route imports those two by direct path (`@/features/guestbook/{actions,queries}`). This is the **same shape as `@/supabase/client` vs `@/supabase/server` and `@/test` vs `@/test/withRollback`** — a public barrel with server-only members held out — so features are barrel-modules like `core/`, not an exception.

**Queries are feature-owned; `core/db` is client + schema only.** `listGuestbook`/`createGuestbookEntry` moved from `core/db/queries/` into `features/guestbook/queries.ts` (they are business logic, used only by the feature). The `core/db/queries/` directory is **removed**. `core/db` keeps the Drizzle client (`db`, server-only) and the **central schema** (the shared relational model, reached via `@/db`) — a feature query imports `{ db, <table> }` from `@/db`. Schema stays central deliberately: a Postgres/RLS app is inherently cross-cutting (FKs, RLS, join tables), `drizzle-kit generate` wants one schema source, and per-feature tables would force cross-feature imports the layering rule bans. `core/db/index.ts`'s `export *` forwarding is now eject-invariant, so it and the (removed) `queries/index.ts` drop out of the eject restore map.

**Layering is a DAG — `app → features → components → core`, imports point only down** — enforced by oxlint `no-restricted-imports` `patterns` in per-zone `.oxlintrc.json` `overrides`: `core/` imports none of the others; `components/` imports neither `app/`/`features/` **nor the data layer** (`@/db`, `@/supabase/server`) so reusable UI stays presentational and data-free; `features/` imports no `app/` and no other feature via `@/features/*` (intra-feature is relative). fallow boundary zones were considered (semantically ideal) but oxlint won: it already runs in the fast `pnpm check` + pre-commit gate, whereas `import/no-restricted-paths` (the zone rule) is unimplemented in oxc. Each override re-declares the react-memo `paths` ban because oxlint replaces (not merges) a rule's options per override.

_Why:_ the old split tied a "reusable" component to a route (`components/guestbook` imported a type from `app/.../actions`) — direction backwards. A feature layer gives each domain one home for its full stack, makes `components/`/`core/` genuinely reusable, and machine-checks the boundary instead of trusting convention. _Trade-off:_ a per-zone override block, and the DB relational model lives centrally while its queries live in features (a deliberate split — the model is shared, the access is feature-local); cross-feature isolation is enforced via the `@/features/*` ban, but intra-feature relative imports are unchecked, and "only `queries.ts` may touch the raw `db` client" is convention, not linted (oxlint globs can't express the negation).

_Amended by ADR-0025: features own their data access as `fetch` wrappers instead of server queries and actions; the layering and its oxlint enforcement stand._

### ADR-0010 — Canonical example slice, replaced-not-deleted; `pnpm eject:examples`

**Accepted.** The template ships one interlocking `guestbook` slice exemplifying every core feature pattern: Drizzle table + companion RLS migration, server-only data-access fns, a Server Action (react-hook-form + zod + `useActionState`), a feature RSC + presentational list, the first testid `T` tree, the first `withRollback` integration test and `loc()` e2e, and an `/api/health` Route Handler. Examples are **intentional best-practice references an agent inherits in context**. When building a real feature, an agent **re-points** the pattern — replaces the example's usage with the real one — rather than deleting it, so the pattern is never lost, only re-aimed. For a fresh app with no use for the demo, `pnpm eject:examples` strips the whole slice back to a bare skeleton (`--clean-self` also removes the eject machinery). The slice wires into a few shared files (the `db`/`test` barrels, `messages/en.json`) via re-exports; eject reverts those from committed pristine snapshots under `scripts/eject/`, drops the `guestbook` i18n key, and removes generated artifacts (migrations, `supabase-types.ts`). Correctness gate: a worktree run of eject must leave `pnpm check` + `pnpm build` green.

_Why:_ a fork (agent or human) gets a working, best-practice reference for each pattern instead of a blank slate, plus a one-command path back to bare when the demo isn't wanted. _Trade-off:_ the slice must stay wired through a small, documented set of shared files so eject remains a mechanical manifest operation.

_Superseded by ADR-0020: the `guestbook` slice and `pnpm eject:examples` were removed when the app became `fintechers-aml`; the first real feature is `src/features/review-queue/`._

### ADR-0009 — `@/test` barrel excludes `withRollback` (second no-barrel exception)

_Amended by ADR-0016: `withRollback` was replaced by `@/test/db`; the barrel rule below is unchanged, only the module it names._

**Accepted.** `src/core/test/index.ts` re-exports `loc` and `T` but **not** `withRollback`. The guestbook e2e (Task 9) was the first thing to load a page using the `@/test` barrel from a real Next.js dev bundle — `GuestbookForm` (a Client Component) imports `T` from `@/test`, and webpack statically resolves every module reachable from that barrel, including `withRollback`'s `await import("postgres")`. `postgres` needs Node builtins (`tls`, `net`, …) with no browser shim, so the dev server 500'd (`Module not found: Can't resolve 'tls'`) on `/guestbook`, timing out the e2e's `fill()` calls. Lazily importing `postgres` inside `withRollback` (ADR-adjacent fix in an earlier task) wasn't enough — webpack still resolves a dynamic import's target for chunking even if it never executes client-side. Fix: drop `withRollback` from the barrel; integration tests import it via the deep alias, `@/test/withRollback`, same shape as the `supabase` exception below. This amends ADR-0007's "supabase is the one exception" — read it as two exceptions now.

_Why:_ keeps `@/test`'s root barrel genuinely browser-safe for `T`/`loc` consumers without giving up the deep-import escape hatch for the node-only test helper. _Trade-off:_ `withRollback` callers must know to reach past the barrel — same trade-off already accepted for `supabase`.

_Superseded in part by ADR-0021: the `@/test` root barrel is removed with `loc`; every `@/test` member is a deep import._

### ADR-0008 — Zod message i18n: per-parse next-intl error map, Zod default fallback

**Accepted.** Localize Zod v4 validation messages through a small per-parse error map (`@/validation` → `zodErrorMap(t)`), **never** a global `z.config()`. Defaults stay Zod's built-in (English); a `validation` message namespace whose keys mirror Zod's issue taxonomy overrides only the codes it defines, and any untranslated code returns `undefined` to fall through to Zod's default. Wire it per parse at each boundary — `schema.safeParse(input, { error: zodErrorMap(t) })`, or `zodResolver(schema, { error: zodErrorMap(t) })` on the client. Keys are derived from the issue by convention (`too_small.<origin>`, `invalid_format.<format>`, missing field → `required`), so the mapping lives in the message catalog, not in code.

_Why:_ `z.config()` mutates module-global state, which races across concurrent RSC / Server Action requests; a per-parse map carries no shared state and is safe under Next.js concurrency, server and client. Extends ADR-0005 (writes via Server Actions + `react-hook-form` + `zod`). _Trade-off:_ callers pass the map explicitly at each parse site (vs. a one-time global), and one documented cast bridges next-intl's statically-typed keys to runtime-derived ones.

_Superseded by ADR-0025: with i18n removed there is no translator to back the map; `@/validation` is deleted and Zod's English defaults stand. The per-parse (never `z.config()`) rule still applies if message overrides come back._

### ADR-0007 — `src/core/` for shared infrastructure; bare per-module aliases

**Accepted.** All cross-cutting infrastructure lives in `src/core/`, **one module per concern** — a folder with a deliberate `index.ts` public API (`db/`, `hooks/`, `i18n/`, `supabase/`, `test/` incl. `test/ids/`, `utils/`), or a flat `<name>.ts` for a single cohesive file that won't grow (`env.ts`). Both resolve through the same bare alias. Top-level `src/` is therefore exactly `app/`, `components/`, `core/`, `docs/`, plus `middleware.ts` (Next.js only auto-discovers it at `src/middleware.ts`). Consolidated from the prior `src/{db,test,lib,testids}` layout; the 1-line `src/i18n.ts` next-intl shim was deleted (`next.config.ts` points the plugin at `src/core/i18n/request.ts`).

Each core module gets a **bare alias** in `tsconfig.json` `paths` — `@/db`, `@/env`, `@/hooks`, `@/i18n`, `@/test`, `@/utils` — while `@/*` → `src/*` covers `@/app`/`@/components`/`@/middleware`. Consumers import only through the root alias (`import { cn } from "@/utils"`), never `@/core/…` or a deep internal path; `index.ts` files name exports explicitly (no `export *` grab-bags). `supabase` is the one exception — it has **no** root index because `server.ts` is `server-only`, so callers import `@/supabase/client` or `@/supabase/server` to keep server-only code out of client bundles. **Amended by ADR-0009:** `@/test` is a second exception (excludes `withRollback` from its barrel for the same client-bundle reason). **Amended by ADR-0011:** `src/` now also contains `features/` (vertical slices); that layer is intentionally non-barreled — features are imported by direct path, not a root alias.

_Why:_ one obvious home for infrastructure; fewer top-level folders; uniform short imports; and the bare alias decouples the import path from the physical location, so moving a module within `core` doesn't churn every importer. _Trade-off:_ a `paths` entry per core module, and a one-time mechanical import rewrite.

_Superseded in part by ADR-0021: `src/core/supabase` and its aliases are removed._

### ADR-0006 — Commit-quality gate via Claude PreToolUse hook; husky dropped

**Accepted.** Removed husky (+ the `prepare` script and `.husky/`). The gate (`.claude/hooks/pre-commit.sh` — typecheck + lint + format:check + changed unit tests) now runs as a Claude **PreToolUse** hook on `Bash(git commit *)`: it blocks the commit (exit 2) on failure and feeds the output back to the agent. _Why:_ commits are largely agent-driven, so a tool-agnostic git hook earned little; this keeps one hook system (`.claude/`), drops a dependency + `prepare` step, and gives the agent inline failure output. CI remains the backstop for non-agent commits. _Trade-off:_ commits made outside a Claude session (human terminal/IDE) are no longer gated locally — accepted, since CI still gates them.

### ADR-0005 — Data fetching: RSC + Server Actions; no client query lib, no axios

**Accepted.** Reads via Server Components calling `src/db` service functions; list state (pagination/filters/sort) via URL `searchParams`. Writes via Server Actions + `react-hook-form` + `zod`; cache invalidation via `revalidateTag`/`revalidatePath`; optimistic UX via `useOptimistic`/`useActionState`; realtime via the Supabase Realtime browser channel. **No TanStack Query / SWR globally** — RSC + React 19 already own caching/dedup/invalidation; adopt locally only for a proven client-cache-heavy surface (YAGNI trigger, not a foundation choice). Native `fetch` for server-side external calls; **no axios/ky/ofetch**. _Why:_ leverage the framework fully, one source of truth, smallest bundle.

_Superseded by ADR-0025 for the frontend: there is no server in a client-only SPA, so reads and writes go to the Kotlin engine (ADR-0024) over `fetch`. The "no client query lib, no axios" position stands._

### ADR-0004 — Canonical specs committed in `docs/`; drafts stay out of git

**Accepted.** Canonical architecture and foundation specs live committed under `docs/` so a fresh clone / CI / cloud agent always has them. Working drafts and plans-under-review stay out of git (gitignored). _Why:_ reproducibility for autonomous agents, while keeping half-baked drafts out of the history.

### ADR-0002 — React Compiler; ban `useMemo`/`useCallback`/`memo`

**Accepted.** React Compiler handles memoisation; `no-restricted-imports` blocks manual memo hooks. _Why:_ removes a class of stale-dependency bugs and noisy code; the compiler is more reliable than hand-tuning.

### ADR-0001 — oxlint + oxfmt over ESLint + Prettier

**Accepted.** Lint via **oxlint** (config in `.oxlintrc.json`) + format via **oxfmt**, instead of ESLint + Prettier. _Why:_ speed and a single Rust-based toolchain; the agent-critical rules (`max-params: 3`, `complexity: 15`, import hygiene) are configured equivalently.
